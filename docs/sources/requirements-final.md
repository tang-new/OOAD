## 1. 项目定位、业务边界与术语

### 1.1 定位

统一权限中心服务两种业务系统：

- `rbac-center`（建议标识，最终以现有配置确认）：权限中心自己的管理前后端，必须被自己鉴权。
- `course-project-management`（外部契约已明确）：课程项目管理系统，对接统一登录、菜单/按钮权限、API 权限与统一身份审计。

权限中心持有：**用户统一身份、角色及继承、角色权限、系统注册、菜单/按钮资源、API 操作资源、角色指派资格、令牌撤销、鉴权决策、集中审计记录**。课程中心持有：**课程、教师、学生、教学班、组、里程碑、提交、评分等业务对象和对象级授权判断**。课程中心可独立部署运行，但本阶段验收需要安排两个系统在同一个或可互联的 Docker Swarm 集群完成联调演示。

### 1.2 RBAC 定义（不可混淆）

- RBAC0 = 用户、角色、权限与用户—角色、角色—权限关系。
- RBAC1 = RBAC0 + **角色继承有向无环图（Role Hierarchy DAG）**；必须处理多父角色、传递继承、去重和环检测。
- RBAC2 的 SSD、DSD、角色基数等约束与 RBAC3 **不属于本阶段**。部门内角色“可指派资格”是本阶段组织管理业务限制，不能冒充 RBAC2。
- **菜单/按钮层级树不等于角色继承 DAG**。前者描述资源导航/展示，后者决定有效权限；API 是独立资源，必须有显式映射，不能因为菜单可见就认为其所有 API 已授权。
- **角色身份不等于业务身份**。`teacher`/`student` 等全局角色由权限中心表达；“某教师是否教授班级 101”“组长是否属于本组”由课程中心检查。

### 1.3 统一语言与字段含义

| 术语 | 本阶段唯一含义 |
|---|---|
| System / Application | 被权限中心纳管的系统；系统码全局唯一 |
| User / Subject | 统一身份用户，`subject` 与 JWT `sub` 关联 |
| Department | 单公司下用户唯一所属部门；可有部门树；**不是 RBAC 权限或数据范围** |
| Role | 归属目标系统或有清晰公共作用域的角色；拥有直接权限、继承规则和状态 |
| Role Inheritance | `seniorRole inherits juniorRole`；高级角色获得低级角色权限，方向在数据库列名与接口都要统一 |
| UserRoleAssignment | 用户与角色的指派关系；额外检查所在部门的角色准入资格 |
| Frontend Permission | 菜单/路由/按钮能力码；只负责前端可见性与互动性，不能替代服务端鉴权 |
| ApiOperation | `(systemCode, operationId, method, pathTemplate)` 登记的后端 API 元数据 |
| Api Permission | 使用 ApiOperation 解析出的全局接口调用要求；API 权限与菜单权限可以关联但不可相互隐式替代 |
| Effective Roles / Permissions | 直接角色及其传递继承、有效状态过滤后计算的可用角色/权限集合 |
| Authorization Decision | `ALLOW/DENY + reason + traceId`；正常无权限与系统异常需区分 |
| AuditLog | 可查询的业务安全事实记录，独立于 Logback 运行日志 |
| DTO / VO / BO / PO | DTO 输入；VO 输出；BO/Domain 承载业务规则；PO/JPA Entity 持久化，不向前端泄漏 |

### 1.4 旧需求收缩、保留与弃用

- 当前代码仍可含多公司、跨公司、角色数据范围、自身部门操作范围、统计及演示 Mock；这些属于第一阶段遗留能力。优先给出数据库与接口影响报告，再按以下规则收缩，**不能不经评估直接删除表和真实数据**。
- **只管理一个公司**：后续不提供公司 CRUD，不引入多租户能力。旧 `company` 表如被 FK/历史数据引用，采用兼容迁移/保留只读或改表方案，经迁移测试后再退役。
- **一个用户属于一个部门**：支持部门树供人员归档、部门角色准入与管理员管理范围使用；禁止同一用户多个所属部门。总部管理员可管理所有下级部门。允许管理员在本部门及授权下级范围指派准入角色，但不可越权授予比自己更高的权限。
- **不实现资源级数据范围过滤**：去掉如“可以查看某部门的所有业务记录”“跨公司查看业务数据”等旧 Data Scope 功能；保留必要的部门管理权限约束，但在文档和模型中明确二者不同。
- 系统已不再需要 `rbac-mock-biz`：课程中心替代 Mock 成为真实接入方。
- 不做历史方案中的热力图、性能图表、风险治理、动态职责分离、临时授权、复杂策略模拟；必要的Dashboard 大屏、基本日志查询、简洁运行健康检查继续保留。

| ID | 要求 | 可观察的验收结果 |
|---|---|---|
| ROLE-01 | 角色 CRUD、单独启停 API，角色码在系统内唯一 | 修改角色名称不改变状态；状态修改有独立端点 |

**数学定义（必须体现在测试中）**：设 `DirectRoles(u,s)` 是用户在系统 `s` 的有效直接角色集合；`Ancestors(r)` 是角色 `r` 可传递继承的低级角色集合（请在源码里把 senior/junior 方向命名一致）。则 `EffectiveRoles(u,s) = DirectRoles(u,s) ∪ ⋃ Ancestors(r)`，先排除停用角色与停用系统，再对各有效角色的直接权限取并集。部门资格在**赋予角色及部门变更**时判断，不以部门表替代角色权限计算；权限撤回与状态变化立即使相关缓存失效。

**已经核实的一条旧变更**：`需求更改.md` 写“删除角色要把所有角色权限删掉以空白角色进入新部门”。**指的是**：变更部门不修改角色定义、角色的全局权限及继承图，只回收该用户不再符合部门准入的指派；永久删除角色才按策略清理其绑定并留历史审计。

| AUD-03 | 记录登录/退出、角色与权限变更、角色继承变更、拒绝鉴权、敏感业务变更的事实 | 能按时间、操作者、目标追溯，不只在控制台打印字符串 |

| AUD-05 | 采用同步审计日志写入；保证业务成功与审计一致性要求 | 数据库写入失败、服务重启与 HTTP 请求重试下不丢已确认记录、不重复写 |
| AUD-06 | 保留用户/系统/操作/对象/结果/原因/requestId/traceId 等最小字段 | 关闭日志 DEBUG 不影响核心审计落库与查询 |

### 3.6 前端（UI）

- UI-01：现有 Vue3/TS 前端继续运行，支持通过配置指向 structured 或 DDD 服务（默认 structured），不改业务源码即可切换；同一接口行为/数据一致。
- UI-02：保留用户、部门、角色、角色继承 DAG、角色指派、菜单按钮及 API 权限管理、系统切换、操作审计查询、登录/退出和 403/404 状态页；优先复用原组件。
- UI-03：角色详情可区分直接权限、继承权限与有效权限；对有多个父角色的 DAG 不错误地当成树；循环配置给出明确拒绝原因。
- UI-04：用户列表必须有分页/检索，部门内角色选择可用选项由后端决定；角色状态操作与普通编辑分离。
- UI-05：用 Playwright 对桌面与移动端关键页截图或测试，前端不是纯静态原型；受控按钮能够真实调用后端并产生 Logback 日志。
- UI-06：去掉业务外的 Dashboard 热力图等非必要页面，不以“页面越多”替代需求完成度。

### 3.7 一致性、性能与安全（NFR）

- NFR-01：默认拒绝（fail closed）；缺失映射、token 过期/撤销、签名或 aud 无效、身份服务超时、失效缓存均不得放行。明确 `401` 未认证、`403` 已认证无权、`404` 不存在、`409` 规则冲突、`5xx` 服务异常。
- NFR-02：JWT 至少校验签名、公钥 `kid`/JWK、issuer、audience、iat、exp、jti；权限不嵌入 JWT，按权限服务/缓存实时获取。统一身份用户映射使用稳定 `sub`。
- NFR-03：权限高读低写：可采用 L1 本地短期缓存 + L2 Redis + MySQL，结合权限/角色/用户的版本号或精确失效；**权限撤销下一次访问须生效**，不能仅靠长 TTL。实测值而非杜撰 QPS、P99。
- NFR-04：所有写事务确保 ACID；JPA Repository 为持久化抽象；跨多表变更在 Service 应用层 `@Transactional`，并有并发事务/乐观锁或加锁防护 DAG 环检测与审计一致性。
- NFR-05：安全控制同时覆盖**前端菜单/按钮、网关 API、课程 Service 对象级权限**；不得允许通过伪造 `userId`、`systemCode`、`operationId`、目标路径、X-Forwarded-* 头绕过。
- NFR-06：密码、Bearer、JWT、凭据、完整个人隐私字段不进入 AOP 日志/审计变更快照；敏感字段在审计 `before/after` 中白名单化/脱敏。
- NFR-07：所有外部服务地址、证书、公钥与缓存参数由配置/Swarm secret 提供；不得硬编码本地机器路径或个人账号。

## 4. 核心接口契约（课程中心对接唯一口径）

### 4.1 五个身份鉴权接口

| 方法与路径 | 目的 | 最小要求 |
|---|---|---|
| `POST /auth/login` | 统一账号密码登录 | body `{username, password, systems}`，签发 JWT；课程中心的 aud 为 `course-project-management`；200 `{accessToken, tokenType, expiresIn}`；401/503 |
| `POST /auth/logout` | 退出登录 | 传当前 bearer、撤销 jti；204；后续调用原 token 必拒绝 |
| `GET /auth/me` | 当前用户/角色/前端权限 | 200 `{subject, roles, permissions, name, no}`，只返回当前 audience 的角色与前端权限；401/503 |
| `GET /auth/permissions/{permission}` | 前端菜单/按钮鉴权 | 200 `{allowed: boolean}`，未知权限默认否；400/401 |
| `GET /auth/api-permissions/{operationId}` | 全局 API 鉴权 | 200 `{operationId, allowed}`，未知 operationId 可按外部文档 404，未经授权则 `allowed:false`；401/404/503 |

**必须遵守的细节**：

1. JWT payload 的示例包含 `sub`、`aud`、`iss`、`iat`、`exp`、`jti`，**不包含角色与权限**。角色权限随配置变化从服务端获取；不能仅前端解析 token 声称有权限。
2. 课程中心文档的 `operationId`（如 `listAdminCourses`）是**API 唯一逻辑操作码**，不能用菜单名称、URL 文案临时拼接；同系统内唯一，路径/HTTP method 与其明确绑定。
3. **暂时不考虑** `aud` 有多系统取值时会产生目标系统歧义：初始交付建议**每次登录只给一个目标系统**。
4. 前端权限检查只决定菜单/按钮 UI；`api-permissions` 只决定全局 API 资格；本课程中心对象级授权仍在其自身 Service 完成。
5. 使用契约测试校验课程中心 `Authorization: Bearer`、错误码和 JSON 字段。允许在本项目外观 `/api/v1/` 版本化，但对课程中心提供的 `/auth/*` 路径**必须可直接调用**，如需重写路径必须在网关做明确兼容映射。

### 4.2 两个审计接口（用户最新确认：都要完成）

**POST `/auth/audit-logs`**（201）：兼容如下 JSON 字段；额外审计字段可内部生成，但不得破坏契约。

```json
{
  "requestId": "d385ab22-0f51-4b97-9ecd-b8ff3fd4fcb6",
  "type": "score_changed",
  "objectType": "term",
  "objectId": "42",
  "target": "课程/小组/目标对象的可读名称",
  "before": {"status": "DRAFT"},
  "after": {"status": "PUBLISHED"}
}
```

- `requestId` 是业务操作生成且在重试时保持不变的幂等键，数据库唯一索引约束；同键同内容返回**同一日志**，同键不同内容明确冲突；课程中心已发布的 POST 审计响应仅枚举 400/401/403/503/201，**对外默认使用契约内的 400 + 稳定冲突错误码**，除非外部契约正式增加 409。
- 服务端从鉴权上下文确定 actor、systemCode、记录时间，不相信调用方伪造操作者；绑定 `traceId`、来源 API、结果与必要的错误原因。外部接口默认只允许经认证的业务服务/当前用户授权调用，不允许普通用户伪造他人业务审计。
- 201 返回 `{id, at, actor, type, target, before, after}`；重试同键时返回同一条记录；参考公开契约的 400/401/403/503。
- 不将密码、完整 token、私有录音、敏感个人信息放到 before/after。

**GET `/auth/audit-logs`**（200）：支持 `actor`、`actorId`、`target`、`from`、`to`、`page`、`pageSize`；响应 `{page,pageSize,total,items}`；空数据时 `items=[]`，限制最大 pageSize，参数非法返回 400。分页顺序稳定（时间降序 + id 作为 tie-breaker），必须具备审计查看权限，并按目标系统隔离。课程中心对教学班/老师可见范围的进一步过滤**仍在课程中心 Service** 执行：权限中心不存课程业务组织表、不直接推断教学班范围；需要携带或允许根据 `objectType/objectId/target` 精确过滤的最少元数据。

公开契约标注 `/auth/audit-logs` 属于统一身份平台，课程中心不建本地审计表。因此**中心端是权威审计存储，课程中心只调用**；本项目作为**统一身份中心服务端**可在自己的数据库创建 audit_log，不违反“课程中心不保存审计副本”。

### 4.3 审计实现方案（本阶段仅采用简单同步审计日志）

定义接口 `AuditWriter`、`AuditReader`，持久化 `audit_log`（request_id 唯一），Logback 运行日志与数据库审计记录严格分离。

**直接同步记录**：权限中心自身重要操作在本地事务中同时写业务表 + `audit_log`；任一必要写入失败则按事务规则回滚，不将失败操作记录为成功。外部课程中心业务事务成功后同步调用 `POST /auth/audit-logs`，权限中心校验身份和幂等键，并在审计记录提交到数据库后返回 201。HTTP 超时或失败可由调用方使用原 requestId 重试；不引入消息队列、发布/订阅、Outbox、消费者或异步审计任务。

- `POST /auth/audit-logs` 的公开契约是 **201 且返回已创建的审计日志**；HTTP 入口必须同步保证审计权威库已提交后返回 201，数据库写入失败不得报告成功。
- 必须验证请求重试和并发请求下的幂等性；业务失败不记录成功审计。跨系统业务提交成功但同步 HTTP 审计失败时，应明确返回/记录失败并允许使用相同 requestId 重试，不声称跨数据库操作具有单事务原子性。
- 业务成功、权限拒绝、异常失败使用不同审计类型/结果；不把审计接口自身的写入无限递归审计。

### 4.4 API 网关与后端校验

标准路径：`Client → Gateway (JWT/iss/aud/jti/ApiOperation/GlobalPermission) → CourseService(业务对象约束) → Business result`。网关只能转发**明确白名单**上游，必须禁止任意目标 URL 的开放代理或伪造系统标识。`operationId` 根据可信 `(HTTP method, normalized route pattern, target system)` 服务端解析，用户不能自行传任意 operationId 欺骗网关；不能按字符串前缀匹配敏感操作（如 `/users/{id}`）。

若课程中心内部已经通过 Spring Security JWK 校验并在 Service 层做全局与对象检查，可将网关设为第一道强制校验，课程 Service 保留第二道强制校验；不能因为网关已授权就删掉业务后端保护。网关故障、权限服务错误均 fail closed；401、403、503 区分日志与返回。

## 5. 双后端架构与迁移约束

### 5.1 目标目录（建议；允许基于仓库现状微调，但必须解释）

```text
OOAD/
├── pom.xml                         # Maven 聚合
├── rbac-contract/                  # OpenAPI、统一错误码、Flyway 迁移、共享测试夹具/契约
├── rbac-structured/                # 面向功能/结构化实现 RBAC1，保留原有行为
│   ├── controller/
│   ├── service/                    # 事务脚本，过程式处理业务规则
│   ├── mapper/                     # JPA 持久化访问抽象
│   └── ...
├── rbac-ddd/                       # 面向对象设计 RBAC1，独立可启动
│   ├── interfaces/ or adapter/     # REST DTO/VO/HTTP 接入
│   ├── application/                # 用例编排、事务
│   ├── domain/                     # 实体、值对象、聚合、领域服务、Repository 端口
│   └── infrastructure/             # JPA Adapter、缓存、外部服务、AOP/审计
├── rbac-web/                       # 同一份前端，运行时配置选后端地址
├── deploy/                         # 同一套可参数化 Swarm stacks/compose

```

1. 保留两个后端为**两个可独立构建/启动的工程**，默认前端指向 structured；通过环境变量 `VITE_API_BASE_URL` 或反向代理 upstream 指向 DDD，不能写死端口，也不能用“同一 Service 加 if/else”冒充两个体系结构。
2. 双后端使用**共同契约和兼容的数据库模型**，但不得把业务核心规则集中到一个共享 service 从而抹平两种设计差异。可共享纯契约/枚举/测试夹具/迁移定义，不共享处理层的角色计算算法实现；相同行为由共享黑盒测试保障。
3. 生产可以仅有一个选定后端承接权限数据写入；联调/对比测试采用隔离数据库、隔离缓存命名空间、不同端口和相同 seed，防止两个版本并发修改造成假故障。若要求并行生产提供两个入口，需专门验证迁移/事务/一致性。
4. Flyway **不追加**新版 migration，不需要备份后才实际变更，直接进行重构以适应下一阶段的目标。
5. 现有仓库源自 Spring Boot 3.3/JPA/Java21；课程中心 `Conversation.md` 中出现 Boot 4.x 技术约定仅作为参考，**不要未经兼容测试跨工程照搬版本**。

### 5.2 结构化方案约束

- Controller 接收请求、参数校验与 DTO；Service 按用例过程操作 Mapper/Repository/事务。实体可为贫血 JPA Entity；不强加领域聚合、复杂工厂、领域事件驱动规则。
- 角色继承查询、循环检测、授权指派、有效权限解析和缓存失效都要实现，不因为采用结构化方法而省略业务。
- 使用共享请求/响应契约和测试；包图与顺序图应真实呈现 `Controller → Service → Mapper` 的中心逻辑。

### 5.3 DDD/OO 方案约束

- **战略设计**：权限中心一个聚焦的授权业务限界上下文；外部课程中心是独立业务系统。复杂部门/角色功能不要机械拆成七个微服务或二十几个子域；不建议使用适配器/ACL，如果有必要使用，必须有理由说明是为了隔离外部 API 模型差异，而非术语堆砌。
- **战术设计**：推荐 `Role` 聚合（角色状态/直接权限与不变量）、`RoleHierarchy`（DAG 边、环判断可能需领域服务协同查询）、`RoleAssignment`/`DepartmentRoleEligibility`（指派与资格），`Permission` / `ApiOperation` / `Menu`、`AuthorizationDecision` 值对象、`AuthorizationPolicy` 领域服务、`AuditLog`、Repository 接口。
- **GRASP**：Information Expert 把角色状态/直接权限规则放到 `Role`；Creator 把相关新对象创建责任放在聚合/工厂；Low Coupling/Indirection 通过 Repository/外部系统适配器；High Cohesion 控制应用服务仅编排；Polymorphism 可在真正存在不同授权资源类别时使用；Pure Fabrication 可为授权解析器/工厂/映射器服务。没有实际变化点不要硬塞模式。
- **分层依赖**：`interfaces → application → domain`，基础设施实现 domain Repository 端口并依赖域模型；domain 不依赖 Spring MVC、JPA Entity、Redis、`RestClient` 或外部课程 API SDK。
- **事务**：应用服务开启事务、加载聚合、调用行为、保存、记录、审计；领域对象的真实业务方法不能只是 getter/setter 包装。API 输入 DTO → Command/BO 应用边界 → Domain 行为 → Result/VO，使用 CloneFactory 复制相容字段，派生字段/身份/审计/敏感字段显式处理。
- **CloneFactory**：按源码所支持的 `@CopyFrom`、`@CopyTo`、`@CopyNotNullFrom` 等注解配合 `CloneFactory.copy`/`copyNotNull` 使用；不能复制密码/JWT、不可变 ID、业务决策字段或把 Entity 无脑覆盖。DTO→领域创建、Domain↔PO、Result→VO 的映射均需明确转换边界和单元测试。**对外输出 VO，不直接暴露 BO/Entity**。
- 课程中心的 `projectmgt-code-conventions` 和 `uml-class-sequence-diagrams` 两份 ZIP 为参考写法；不能直接将其对 `cn.edu.xmu.projectmgt` 的具体包名、脚本路径、Apifox projectId、Spring Boot 版本当成我方项目事实。

### 5.4 数据库变更建议（正式建表前对照当前 ER 与 Flyway）

应明确或调整以下逻辑数据实体和约束：

- `sys_user`（subject/所属 department_id 唯一非空策略/状态/乐观版本）、`department`（parent_id/tree），**单公司**；现存 company 兼容策略单独写明。
- `software_system` / `application`（code/status）、`role`（system_id/code/status）、`permission`（system_id/code/type）、`user_role`（user_id/role_id 的唯一键）。
- `role_hierarchy`（senior_role_id,junior_role_id 唯一；无自环；同系统；DAG 在领域服务/事务中检查）、`role_permission`（role_id,permission_id 唯一）。
- `department_allowed_role`（department_id,role_id 唯一；表名可不同），与 `user_role` 分开，不允许把部门带进角色直接权限关联。
- `ui_resource`（system_id,parent_id,type=MENU/BUTTON,route,permission_code,sort）、`api_operation`（system_id,operation_id,method,path_template,required_permission,enabled），及必要的 `ui_api_mapping` 显式关联。
- `audit_log`（request_id 唯一、system_code、actor_id、event_type、target、before/after 脱敏 JSON、created_at、trace_id、result 等索引）。

实际 schema 可复用现有 `resource`、`action`、`permission` 和迁移，只需逻辑上达到这些约束；避免为迎合表名重建所有表。删除/更新采用 FK 约束及业务规则，优先逻辑停用而不是危险级联删审计。

## 6. 日志、缓存、并发与协议落地

### 6.1 日志（Logback + AOP）

- `LayerLoggingAspect` 类似统一切面覆盖 API/Application/Infrastructure 包，记录 `traceId, layer, class, method, durationMs, result, exceptionType`。避免混乱重复打印；级别使用 Spring `logging.level` + `logback-spring.xml` appender/格式，部署时可调整 DEBUG。
- 在角色赋予、撤销、继承边变更、鉴权拒绝、审计写入等关键路径输出可识别的**结构化审计记录**，并进行正式存储；AOP 日志无法替代查询接口。
- 即使方法异常也应留下调用结果日志；不在业务异常上打印密码/请求体；避免 AOP 重入与自调用漏记（Spring Proxy 自调用不拦截时要有测试/显式替代机制）。

### 6.2 多级缓存及短路

- 候选路径：token 无效/系统停用/用户停用立即短路拒绝；查 L1（版本一致）→ L2 Redis → DB，计算有效角色权限；发现明确 `DENY` 可在受控小 TTL 条件下缓存但必须版本失效；超级管理员策略不得绕过用户有效性/系统 audience 检查。
- 角色权限/继承/角色状态/用户指派/UI-API 映射变动后，事务提交后更新权限版本/清理受影响缓存；并发写下不允许旧缓存回填覆盖新版本。重要写操作落库与版本变更同事务；短路不得导致审计失败决策不记录。
- 提供并发测试：同时给 A→B 和 B→A 加边，不能均成功；权限撤销后两端的下一次 API 调用必须拒绝；L1/Redis 层失效重建一致。

### 6.3 外部接入与异常处理

- 网关/业务使用明确超时与重试（只重试幂等或有 requestId 的接口）、熔断/拒绝策略和关联 traceId。
- 不引入消息系统，不增加未必要的技术依赖。AOP 不负责审计落库，审计由业务用例同步写入。
- `GET /auth/audit-logs` 的查询条件不应设计成课程中心 `termId/classId` 的强耦合字段；由课程 Service 做对象级范围过滤，或使用事先约定的规范化 target/objectId 做局部查询。

## 7. 设计文档、UML 与两种范式对比

### 7.1 必交文档

- `docs/requirements.adoc`：本阶段 SRS；需求表每行有编号/前置条件/正常流/异常/验收方法。
- `docs/architecture-structured.adoc`、`docs/architecture-ddd.adoc`：同一行为下包结构、职责、依赖方向、事务、缓存与审计的具体区别。
- `docs/database.adoc` + ER（与迁移一致）；`docs/api.adoc` 或链接到唯一 OpenAPI；`docs/test-plan.adoc` + JaCoCo。
- `docs/iteration-log.adoc`：每次真实迭代的 commit hash、需求变更、图/代码/测试链接、为何修改。可生成 README 或索引但不要伪造旧历史。
- `docs/diagrams/`：用可维护源码生成的包图、关键类图、顺序图、角色 DAG / 必要状态图，导出可看清的 SVG/PNG，并**目视验证**；图中的类、字段、方法须与提交代码一致。

### 7.2 开始编码前就锚定的 UML 对照案例

| 案例 | 两后端是否同外部流程 | 结构化图要点 | DDD 图要点 |
|---|---|---|---|
| S1 创建角色继承关系并检测环 | 是 | Controller → Service 查询边 + 判断 + Mapper | AppService → RoleHierarchyPolicy / Domain Service → Repository |
| S2 用户角色指派（部门资格/越权检查） | 是 | Service 事务脚本检查所有条件 | Assignment/ApplicationService 调用领域对象行为、Repository |
| S3 计算用户有效权限（传递闭包/去重） | 是 | Service/Mapper 过程化遍历 | Role/AuthorizationPolicy 按职责协作 |
| S4 课程中心 API 网关鉴权 | 是 | 校验器调用鉴权 service 和 API 映射 | 接入层 + AuthorizationPolicy/ApiOperation 领域模型 |
| S5 审计同步写入 | 是 | Service → 审计 Mapper → audit_log | AuditApplicationService → AuditRepository → audit_log |
| S6 修改角色状态/缓存失效 | 是 | 处理过程 + 数据访问 | Role 状态变化方法 + 领域事件与投影/失效服务 |

**必须保持相同**：用例、外部接口方法与响应、RBAC1 角色继承语义、数据库逻辑实体关系、业务验收结果。**应该不同**：内部代码/包依赖与核心职责、类关系、顺序图的消息接收者、领域状态与规则归属、仓储端口、事件与适配器。不能为了“图必须不同”而篡改业务，也不能复制结构化的贫血模型到 `ddd` 目录并改包名。

类图按课程 PPT 使用关联/依赖/实现、泛化、组合等正确 UML 语法，Service 居中仅作为排版建议；顺序图明确 lifeline、调用者、执行条、同步/回复、`alt/opt/loop`，异常分支与事务结果一致。必要时复用两份 ZIP 的规则，但**脚本路径必须以本项目为准**。

### 7.3 面向对象答辩准备

每个案例必须能口头解释：问题与需求 → 对象是谁 → 为什么这个对象拥有该行为（GRASP）→ 为什么用或不用工厂/适配器/策略/事件 → 和结构化方式的依赖、复用、内聚、变更影响有何差别 → 实际类/方法/测试/日志的证据。至少分别准备 RoleHierarchy、RoleAssignment、Authorization、Audit 四类场景与各自“结构化版 vs DDD 版”的对照。

## 8. 测试体系及最小验收矩阵

### 8.1 测试方法

- 每条需求至少有一条可执行验收用例并附 ID；编写时先跑出真实 RED 再实现 GREEN 与重构，不通过修改断言、跳过测试或伪造报告达标。
- 等价类：合法/非法用户、角色、系统、部门、权限、operationId、JWT、audit requestId。
- 边界值：0/1/N 个角色、无父/单父/多父、深度继承、环/自环、空/最大字符串、分页边界、审计时段起止、token 过期临界点。
- 异常：失效/停用对象、跨系统串权、并发新建环、JPA 唯一键冲突、Redis 不可用、同步审计数据库写入失败/重复请求、课程中心超时/掉线、业务事务回滚、调用方无权查询别人的审计。
- 技术测试：JUnit5、MockMvc、真实 MySQL/JPA/Flyway 与 Redis、两个后端独立集成测试、共享 API 合同测试、ArchUnit 依赖规则、JaCoCo、Vue 测试及 Playwright E2E。不得仅使用 Mock 验证关键 DB 一致性。

### 8.2 必须可演示的基准用例

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | 登录课程中心 audience，调用 `auth/me` | 本人系统角色与前端权限正常，JWT 无权限 Claim |
| T02 | 课程中心 token 访问权限中心后台 | 401/403，不能串系统 |
| T03 | A 继承 B，B 继承 C | A 取得 B/C 权限并去重 |
| T04 | A、B 都继承 C | 菱形图有效权限唯一 |
| T05 | 新增 C 继承 A 形成环 | 409/业务错误，不入库 |
| T06 | 同系统角色 + 跨系统角色继承 | 只允许前者，后者拒绝 |
| T07 | 部门未批准某角色但管理员直接调用指派 API | 403/409，无法绕过 |
| T08 | 总部/下级管理员权限差异 | HQ 可以管理被允许的下级，下级不能越权 |
| T09 | 角色停用、直接权限撤销、继承边删除 | 下次鉴权立即正确拒绝，Redis/L1 无陈旧授权 |
| T10 | 前端隐藏按钮但直接请求受保护 API | 后端真实 403，Logback 可查 |
| T11 | API 映射缺失/指向错误路由 | 启动 CI/接口拒绝，不以 200 放行 |
| T12 | 有 API 全局权限，但课程对象归其他老师 | 课程 Service 对象级拒绝 |
| T13 | 无 API 全局权限调用课程接口 | 网关直接拒绝，后端业务未执行 |
| T14 | 使用五个 `/auth/*` 接口校验契约 | 方法、参数、状态码与 Apifox 一致 |
| T15 | `POST /auth/audit-logs` 连续两次同 requestId 同内容 | 两次得到同 id、DB 仅 1 条 |
| T16 | 相同 requestId 但内容不同 | 明确冲突，无覆盖历史 |
| T17 | 审计列表分页、actor/time/target 搜索、越权查询 | 过滤正确、稳定排序、只见授权范围 |
| T18 | 业务事务失败/外部同步审计请求失败或服务重启 | 不产生虚假成功审计，失败可追踪且相同 requestId 重试安全 |
| T19 | 相同 requestId 的审计 HTTP 请求提交 N 次 | AuditLog 幂等、数据库只有一条且返回相同 id |
| T20 | 菜单点击或按钮触发 API → Service → Infrastructure | Logback 可关联 traceId，三个层次有日志 |
| T21 | 同样 API 分别调用 structured/ddd | 成功/错误/DB 状态一致（排除生成 ID/时间等不可比字段） |
| T22 | 两个系统在 Docker Swarm 按目标拓扑部署并访问 | 前后端可用、SSO/网关/审计联调且证据可复查 |

每个测试输入值写入固定测试夹具，避免依赖真实员工隐私数据；JaCoCo 输出分别对应 structured、ddd，并标明核心领域逻辑覆盖。可测量 QPS/延迟时展示测试环境、压测脚本与真实数据，不设未经证明的绝对高并发指标。

### 13.3 学校、课程中心与权限中心的责任边界

```
同一使用者/同一统一 subject
              │
      ┌───────┴────────┐
      │                │
权限中心前端          课程中心前端
      │                │
      │登录/菜单/API鉴权│
      ▼                ▼
统一身份与权限中心 ───► API 鉴权决策 / 审计中心
      ▲                         │
      │                        │只校验全局接口权限
      │                ┌───────▼──────────┐
      │                │课程中心后端 Service│
      │                │课程/班级/组业务判定│
      │                └──────────────────┘
      │
      └─ 维护两系统用户、角色、继承、权限映射，拒绝跨系统串权
```

- **统一身份中心（Identity Provider + Permission Center）**：认证、令牌、系统级角色与有效权限、UI 权限校验、API 全局权限判定、集中审计。真实学校是否提供完整 SSO 属于外部集成事实，不可凭假设替代。课程实验可由本权限系统提供**兼容协议的实验实现**，必须配置好实际信任边界。
- **课程中心**：业务数据真正持有者、全局权限 API 的调用方、对象级授权规则执行者、业务审计数据的生成方。它对 `teacher` 的理解可细到“任课教师”和“课程组长”；这些关系**不能全部迁到 RBAC**。
- **统一日志中心**：集中结构化审计记录。不要与 Logback 的调试事件混淆，也不要让 `GET /auth/audit-logs` 成为可读出所有教务隐私的无权限接口。
- **网关**：负责可信路由解析与第一道 API 强制控制；不能让客户端控制被校验的 `operationId`、系统码或者目标上游 URL。

### 13.4 哪些课程中心业务操作必须作为授权集成示例（不迁移业务实现）

Apifox 公开目录按“学期、课程、教学班、小组、提交/检查、口试与预约、成绩、文件与审计”等业务区域组织。至少选下列**六类有不同授权语义**的真实操作作为映射和测试样本：

| 业务样本 | 全局权限中心判什么 | 课程 Service 还判什么 | 最终证据 |
|---|---|---|---|
| 管理员新建学期与切换当前学期 | 管理身份与 `term.current.manage` 等公开授权码所对应的 API 全局授权 | 学期日期、当前指针及唯一性等领域规则 | 非管理员网关拒绝；管理员改动成功并记录审计 |
| 管理员审核课程 | 管理角色或 `operationId` 对应的全局 API 权限 | 待审状态、操作人是被允许的审核者 | 通过/驳回/重试/重复修改测试 |
| 教师提交课程 | 目标系统教师全局身份及调用资格 | `Course` 是否处于正确状态、教师身份有效 | 教师可创建自己课程，学生不能伪造教师 |
| 课程拷贝 | 公共契约中的 `CC` 课程拷贝全局权限；同时支持本课程组长业务身份例外规则 | “本课程组长”具体由课程中心验证；复制内容与不复制内容的规则 | 组长无 CC 仍可依业务规则；非组长有 CC 时才可调用，具体约束以原系统代码为准 |
| 组长审批入组 | 必要的学生/组长全局 API 调用资格 | 小组现任组长、申请状态、申请人所属班级等 | 换组长后旧组长拒绝，未授权直接调 API 拒绝 |
| 教师记录口试检查/改分 | 口试检查相关全局 API 权限 | 课程/教学班归属、里程碑类型、检查对象成员、已完成状态 | 外部审计 `score_changed` 经 POST 写入并可 GET 查询 |

### 13.5 两个不同的“层级”必须分别讲清

**RBAC1 角色层级（DAG）**：

```
资深角色 A  ── inherits ──► 低阶角色 B ── inherits ──► C
       │                                          ▲
       └───────────── inherits ─────────────────┘
```

- 可有多父/多继承路径，角色权限从被继承的低级角色传递给高级角色。
- 必须检测自环、有向环、重复边、跨系统边、停用状态、继承后权限去重与可追溯来源。

**菜单/按钮层级（树）**：

```
权限中心导航
├─ 用户管理（MENU）
│  ├─ 新建用户（BUTTON）
│  ├─ 停用用户（BUTTON）
│  └─ 用户分页检索（MENU 所在页的 API，不必对应一个按钮）
└─ 角色管理（MENU）
   ├─ 修改继承关系（BUTTON）
   └─ 分配角色（BUTTON）
```

- 菜单树只是 UI 资源组织关系。父菜单可见不应**自动**推导出所有子按钮可用；按钮是否可见要按本按钮权限码判定。
- API 权限是另一类资源，不能把“用户点击过拥有的菜单”当成调用 API 的安全凭证。

## 14. 需求冲突、歧义与重大决策登记（DEC）

> 为了不中断开发，以下写出**安全默认值**。只有明确的老师/用户新增要求才能推翻正式评分项；遇到歧义时保留默认值、提供备选方案与自动化测试，不许无声修改模型。每个条目后续都要在 `docs/decision-log.adoc` 记录决定者、日期、受影响 API/ER/测试。

| 决策号 | 问题与冲突 | 当前建议结论 | 需要保护的验收条件 |
|---|---|---|---|
| DEC-01 | 第一阶段多公司，第二阶段“只需一个公司” | 本阶段不再维护公司 CRUD；迁移保留必要的旧 FK/历史记录，尽量不丢已有真实数据 | 旧数据不会被清库；新 UI 无多公司授权范围 |

| DEC-21 | 草稿注释写“传入 DTO、传出 BO”，老师代码规范却采用“输入 DTO、输出 VO”，课堂 PPT 又区分 BO/DO 与 VO | **本阶段采用对外输入 DTO、内部业务 BO/DO、对外响应 VO 的清晰边界**；如果老师课堂明确要求某一特定对外 API 返回 BO，则仅在该合同上按约定命名/映射，不能直接裸露可变领域聚合/JPA Entity | CloneFactory 在 DTO/Command、Domain/PO、Result/VO 边界工作，领域行为不由字段复制替代 |

### 14.1 不应被隐藏的能力缺口

- 如果 Gitee 课程系统的部署权限不在本组，不能写“已部署”或“已联调”。应提供集群部署计划、教师协调记录、可执行联调脚本及阻断说明；正式验收仍可能因此失分。
- 如果真实学校统一身份没有可用凭据或接口，不能猜测 SSO 密码体系；在受控课程环境内实现本项目身份中心兼容接口并使用演示账号，明确其不是学校生产系统。
- 如果目前 Mock/测试确实依赖第一阶段多公司、数据范围，则删除或重构前应先写旧行为回归测试；对于本阶段**明确废弃**的行为，可更新需求关联测试，但不得静默删掉失败的安全回归。
- 如果无法验证 CloneFactory 在 Spring Boot 3.3.5 / Java21 的注解处理构建，先建立一个独立小型编译和映射安全测试，再接入生产代码；不能靠人工推测 generated class 一定存在。

## 15. 全部业务不变量与规则的可执行定义

### 15.1 身份与系统作用域

`U-01` 同一自然人的统一身份只能由一个稳定 `subject` 表示；用户名、学号或员工号可以作为展示/检索字段，不作为跨系统授权的唯一权威标识。

`U-02` `System.code` 全局唯一；两个系统可以使用同名角色码如 `admin`，但 DB 逻辑键应为 `(systemCode, roleCode)`，不能因同名角色合并权限。

`U-03` `JWT.aud` 包含当前目标系统；角色和权限按当前 `systemCode` 过滤。双系统 SSO 指的是**统一认证主体**，不意味着课程 token 可访问权限中心管理接口。

`U-04` `JWT` 不存角色/权限；至少校验签名、`kid`/密钥轮换、`iss`、`aud`、`exp`、`iat`、`jti`。仅依赖 JWT 自身过期不能满足已注销令牌立即拒绝，必须有撤销表/缓存及可恢复策略。

`U-05` 未登录、冻结用户、失效系统、已撤销令牌在进入任何受保护领域用例前即被拒绝；错误分类与日志均可查。

`U-06` 初始 root/bootstrap 不得依赖“先有管理员才能创建管理员”的死循环；通过**仅在部署初始化允许**的受控迁移/命令行种子建立初始管理员，记录操作者与时间；上线后关闭入口。

`U-07` 用户被迁移部门、停用账号、删除角色后应撤销受影响有效权限并更新授权版本；角色不存在时不残留空引用。

### 15.2 角色层级模型和箭头方向

统一约定：`seniorRoleId` 表示**拥有继承所得权限的高级角色**，`juniorRoleId` 表示**被继承权限的低级角色**。数据库一行 `(seniorRoleId=A, juniorRoleId=B)` 读作 **A 继承 B**；UI 文字“为 A 添加被继承角色 B”。不使用含义不清的 `parent_role_id`，除非字段 Javadoc、迁移说明和图例给出等价定义。

设角色图 `G=(R,E)`，`(a,b)∈E` 表示 `a` 继承 `b`；`Descendants(a)` 在本语义里是从 `a` 沿继承边可达的低级角色集合，定义：

```
Reachable(a) = {a} ∪ {b | a →* b，沿角色继承边可达}
ActiveReachable(a) = Reachable(a) 中通过状态及边界校验的角色
EffectivePermissions(u, s)
  = ⋃ DirectPermissions(r)
    where r ∈ ⋃ ActiveReachable(d) for d ∈ DirectRoles(u, s)
```

该实现须遵守：

- `H-01` **无自环**：A 继承 A 必须拒绝。
- `H-02` **无环**：若新增 A→B 前发现 `B` 已能到达 `A`，则必须拒绝该边并且事务无新增行。
- `H-03` **同系统**：A/B 必须属于同一个被管理系统；跨系统角色引用不合法。
- `H-04` **无重复边**：重复配置 A→B 允许幂等返回已有关系或明确冲突（选一种并写契约），绝不生成两行。
- `H-05` **传递**：A→B→C，A 获得 B 与 C 的生效直接权限。
- `H-06` **菱形**：A→B、A→C、B→D、C→D；D 的权限只出现一次，但来源可保留多条解释路径。
- `H-07` **多直接角色**：用户同时有 R1/R2，最终取并集；不能覆盖、相互排斥或以某个单角色权限作为全部权限（本阶段没有 RBAC2 约束）。
- `H-08` **停用角色**：停用自身的角色不贡献权限；默认不再沿停用节点继续传递，恢复后按图重新计算。若需求规定停用仅影响直接分配而不影响继承，必须改写状态表与测试，否则遵循安全默认。
- `H-09` **批量删边**：删 A→B 后重新算 A 的可达权限，若存在 A→C→B 的备用路径，B 权限仍存在；若无备用路径则失效。
- `H-10` **不可越权改继承**：拥有角色管理页查看权限不等于有新增继承边权限；修改会提升若干用户权限，按敏感变更处理并审计。
- `H-11` **原子性**：创建继承边和环检测必须在一个足够隔离的事务/并发互斥域内完成；并发两条边不能相互绕过检查。
- `H-12` **可解释**：能列出某权限来自直接赋权还是经 A→B→C 继承获得，至少在管理详情/API 输出路径或来源标签。

### 15.3 部门、角色指派和管理范围

- `D-01` 每个有效用户最多**一个当前所属部门**；是否允许未归属部门的特殊系统管理员须作为 bootstrap 例外明确写入 schema。
- `D-02` 部门是人员组织结构和角色准入策略，不直接提供 `Permission`；`Role` 没有被绑定的用户也仍然是有效角色定义。
- `D-03` 角色准入采用 `DepartmentAllowedRole(departmentId, roleId)` 或同义清单；给用户指派角色时检查该用户**当时的所属部门**是否允许该角色。客户端不能携带自称 departmentId 来替代服务端查询。
- `D-04` 对于有继承关系的角色，部门只限制**直接指派资格**；已继承角色不需要逐个部门指派，但提升继承权限须受到有权管理者审核。这样不会扭曲 RBAC1 继承数学定义。
- `D-05` 部门调动：默认先检查新部门准入 → 在事务中更新 `user.departmentId` → 撤销不符合新部门准入的**用户角色指派** → 增量版本/审计 → 返回结果。不得改变共享 Role 对象自身权限，更不得把原部门其他用户角色抹掉。
- `D-06` 总公司/总部管理者对下属部门的用户管理具有范围许可，不等于直接获得其他系统业务权限；管理员对其它系统的配置操作仍要求该系统授权管理权限。
- `D-07` 部门级管理员必须校验 `actor` 可管理的部门范围、可指派的角色及被操作目标用户，而非只看 actor 是否有页面按钮权限。
- `D-08` 角色能否被指派到某部门属于业务策略，`UserRoleAssignment` 和 `DepartmentAllowedRole` 不能错误合并为同一表。
- `D-09` 对于从部门树删除部门，必须先处理在职用户、子部门和准入关系；删除前必须有完整冲突信息，禁止外键级联静默清空用户。

### 15.4 菜单/按钮与 API 的两种不同授权

- `P-01` 前端权限码与 API 全局权限码**分属两个独立集合**；即使同一功能按钮与 API 对应，也不共享“是否访问”的推论。根据真实课程 API，前端权限码可为 `CV/CR/CE/CC` 等，API 全局权限可采用 `AuthorityCodes` 表述，二者不能偷换。
- `P-02` UI 菜单、子菜单、按钮、路由构成至少一棵可遍历的资源树。菜单的可见性可依据其自身明确配置的权限、子项聚合展示策略来确定，但**父菜单可见不自动赋予子按钮权限**。
- `P-03` API 单独登记 `method + normalizedPathTemplate + operationId + systemCode + requiredAuthority`。公开/登录/健康检查类路径应写明合法白名单来源，除此之外未登记 API 默认拒绝。
- `P-04` 权限管理界面显示 `UI Permission ↔ ApiOperation` 的对应关系与未覆盖检查表；该关联是**追踪和权限配置的依据之一**，不代替服务端实际 requiredAuthority 校验。
- `P-05` 直接通过 curl/Postman 调用未授权 API 必须被后端拒绝，不得因为绕过 Vue Router 就成功。
- `P-06` 未授权请求在拒绝后不得进入课程中心业务 Service 的写方法；失败也应保留安全审计元数据而非丢失。
- `P-07` 课程中心业务授权须在课程中心自己的领域层进行，例如“某个班级的任课教师才可以修改该班课程”，中心权限的全局 ADMIN 角色不能自动越过业务不变量。
- `P-08` 用户无任何按钮权限时仍可按需访问“本人资料/退出登录”等明确无需额外业务授权的基本端点，不能意外锁死全部系统；无权限页应该解释缺的权限而非静默空白。

### 15.5 审计与日志的不变量

- `A-01` Logback 方法调用日志 = **运行诊断**；`audit_log` = **长期可查询的安全/业务事实**；两者数据结构、敏感信息策略、保留与访问权限不同。
- `A-02` 审计写入只能由有权主体发起；actor 由可信认证上下文确定，不能由 POST JSON 的任意字段伪造。
- `A-03` 对外 POST 201 时审计权威库已提交且返回稳定 id/at/actor；同 requestId 同内容重试返回同一 id；不同内容冲突不覆盖既有记录。
- `A-04` 课程中心业务审计的生成应发生于**成功的业务事务之后**；对失败尝试可记录独立安全事件，不能谎称业务状态已经变更。
- `A-05` 审计记录通过同步数据库事务写入；只有事务成功提交后才视为已审计落库，数据库失败不得报告成功。
- `A-06` 审计记录包含稳定 `requestId`、来源系统、actor、时间、事件类型、对象标识、before/after 脱敏摘要、correlationId/traceId、结果；不复制密码/令牌/完整业务隐私。
- `A-07` 审计查询过滤支持 actor、actorId、target、from/to 与分页；按系统和查询者许可裁剪。课程班级、教师可见范围的业务过滤继续由课程 Service 执行。
- `A-08` 发生鉴权拒绝时，仍能把拒绝的元数据同步写入安全审计记录，不能因为主流程短路而完全不可追溯。
- `A-09` 审计不得引发无界递归：记录“写审计”请求不再生成同类型审计记录；只在必要时独立记录系统健康/异常。
- `A-10` 关键鉴权配置变更要产生审计，但**日志系统故障的降级策略必须明确定义**：敏感授权操作优先与审计记录在同一数据库事务中保持一致；普通读取可以保留技术日志并按既定失败策略执行，绝不可静默丢弃所有安全证据。
- `A-11` 外部 POST `/auth/audit-logs` 的相同 `requestId` 并发重试应在数据库唯一键下形成一条审计记录；同键异体返回**合同已允许的 400 业务冲突结果**，若未来老师 OpenAPI 正式增加 409 才随版本调整。

## 16. 接口目录、请求/响应和边界语义

### 16.1 外部集成：7 个已由老师 Apifox 确认的接口（必须完全兼容）

本节列的是**课程中心公开合同事实**；详细请求 schema 仍以运行前拉取的最新版 OAS 为准。不得以这里的示例字段去修改老师已经发布的准确类型。课程中心公开入口：`https://s.apifox.cn/775094d6-9f5f-4b75-9600-2332c43948d3`，本轮可见接口更新时间集中在 2026-11-09。

#### EXT-01：POST `/auth/login`

- 目标：从统一身份来源认证主体，为 `systems` 指定的目标系统签发 bearer token。公开描述明确：课程中心本身“不代理、不持久化密码”；新权限中心**作为实验统一身份提供方**可依据实际认证后端校验密码，但课程业务 DB 不得存一套独立密码。
- 输入：JSON 包含 `username`、`password`、`systems` 数组。公开示例中的 `username` 是学号数字 `20220101`，不是“只能输入字符串”的证明；应核对 OAS 类型并在适配边界处理实际形态。
- 响应成功：`200`，`{ "accessToken":"...", "tokenType":"Bearer", "expiresIn":7200 }`（7200 是公开示例，不是强制固定 TTL）。
- 常见异常：`401` 账号凭据错误、`503` 统一认证服务不可用。无效系统 audience/输入字段错误应按最终 OAS/统一错误策略处理。
- JWT：示例 `sub`、`aud`（数组）、`iss`、`iat`、`exp`、`jti`，令牌没有 roles/permissions。密钥、轮换与撤销状态必须真实实现。
- 完成证明：成功登录两个目标系统、错误凭据、停用主体、无效系统、签名验证、前端登录状态恢复、登出后拒绝。

#### EXT-02：POST `/auth/logout`

- 输入：当前已认证 bearer；公开文档声明无 JSON body。
- 结果：`204 No Content`（无响应体）；未认证 `401`。
- 语义：撤销当前令牌 jti；从此网关与权限中心都不能仅因为签名与 exp 合法而继续允许。
- 完成证明：登录 → 正常访问 → logout → 原 token 立即拒绝；多实例与 Redis 重启的撤销策略有持久化边界。

#### EXT-03：GET `/auth/me`

- 输入：Bearer，服务端从 `aud` 判目标系统。
- 成功示例：

```json
{
  "subject": "sso-u1001",
  "roles": ["teacher", "admin"],
  "permissions": ["CV", "CR", "CE"],
  "name": "张小雨",
  "no": "20220101"
}
```

- `roles` 仅当前目标系统的有效角色；`permissions` 仅前端菜单/按钮权限；不能把 API AuthorityCodes 额外塞进 `permissions` 作为未声明扩展。
- 缺少 `sub`/aud、过期或撤销 token：`401`；下游不可用：`503`。用户状态变更或角色撤销后重新 GET 应反映变化。

#### EXT-04：GET `/auth/permissions/{permission}`

- 输入：当前用户 JWT、路径中的**前端权限码**。公开文档明确前端权限码**不是** AuthorityCodes。
- 输出：成功 `200` 且 body **只有业务判断字段** `{ "allowed": true|false }`；参数非法 `400`；未认证 `401`。
- 无权限 ≠ 未登录：对合法用户请求一个存在但无权的前端权限，应返回 `200 allowed:false`，而不是错误地让 UI 以为掉线。

#### EXT-05：GET `/auth/api-permissions/{operationId}`

- 输入：当前用户 JWT + 目标课程中心 API 的稳定 `operationId`，服务端用 `aud` 选系统。
- 输出：成功 `200`，`{ "operationId": "listAdminCourses", "allowed": true|false }`；公开文档列出 `401`、`404`、`503`。
- `404` 用于未知/不再登记的 operationId；存在但无权返回 `200 allowed:false`；网关负责将此 `allowed:false` 转化为对**实际业务 API** 的 403。
- 此接口只查该操作的**全局** AuthorityCodes；课程组长、任课教师、组员、本人等**对象级规则**仍由课程 Service 自己判断。
- 网关不得相信客户端自报 `operationId`，必须从**真实路由配置、请求 method 和路径**映射到正确 operationId。

#### EXT-06：GET `/auth/audit-logs`

- 输入：鉴权主体和 `actor`、`actorId`、`target`、`from`、`to`、`page`、`pageSize` 过滤（公开文档的可选 query 字段）；课程中心按学期、课程、班级和教师范围的过滤**不属于权限中心服务端直接认知的业务模型**。
- 输出：`200`，`{ "page":1, "pageSize":20, "total":43, "items":[...] }`，`items` 的每条记录包含 `id, at, actor{id,name,roles,deleted}, type, target, before, after`。
- 错误：`400` 无效分页或时间范围、`401` 未登录、`403` 无查审计资格、`503` 不可用。对过滤结果必须先授权再分页、排序稳定；空集 `items:[]`。
- 不要求课程中心自身有一张 audit_log 表；权威审计库在**本权限中心**。权限中心内部可额外保留 `objectType`/`objectId` 索引字段，但对外序列化仍以 OAS 为准。

#### EXT-07：POST `/auth/audit-logs`

- 输入（公开示例）：

```json
{
  "requestId": "d385ab22-0f51-4b97-9ecd-b8ff3fd4fcb6",
  "type": "score_changed",
  "objectType": "term",
  "objectId": "string",
  "target": "string",
  "before": {"property1":"string"},
  "after": {"property1":"string"}
}
```

- `objectType: term` 和 `type: score_changed` 在示例中并不自然对应，仅用于说明字段格式；正式事件要提供**真实对象类型**与业务类型组合。
- `requestId` 由课程业务操作生成且重试保持一致；与权限中心审计表唯一键绑定。`actor` 不出现在客户端请求样例中，必须由可信 JWT/调用服务身份提取。
- 输出成功：`201 Created`，原始记录形态 `{id,at,actor,type,target,before,after}`；相同 requestId 同内容重复调用仍返回该同一条记录及 ID。公开错误：`400/401/403/503`。
- 外部成功 `201` **必须**表示审计记录已经同步写入权威数据库且事务提交；不引入异步审计接入，也不改写七个 HTTP 接口。

### 16.2 内部权限管理 API 设计清单（**建议路径，不是对现有仓库已实现的断言**）

先对 `rbac-contract/.../rbac-api.yaml` 做 diff。若已有等价功能路径，优先兼容既有端点并将新增行为拆成清晰 API；以下 `/api/v1` 仅用来说明**完整功能面**：

| 组 | 建议 HTTP 入口 | 明确的功能与授权边界 |
|---|---|---|
| 身份主体 | `GET /api/v1/users?page=&pageSize=&q=&departmentId=` | 分页检索，不直接返回密码、token、历史隐私 |
| 身份主体 | `POST /api/v1/users` | 创建/关联用户，身份源与用户档案一致 |
| 身份主体 | `PATCH /api/v1/users/{id}` | 修改可编辑档案，不混入状态切换或部门迁移 |
| 身份主体 | `PUT /api/v1/users/{id}/status` | 单独启用/禁用用户，有审计与缓存失效 |
| 身份主体 | `PUT /api/v1/users/{id}/department` | 管理员迁移唯一所属部门及角色指派清理 |
| 组织管理 | `GET /api/v1/departments/tree` | 部门树，不把公司/数据范围暴露成 RBAC 权限 |
| 组织管理 | `POST/PATCH/DELETE /api/v1/departments` | 部门管理，删除前检查员工、子树和准入关联 |
| 组织管理 | `GET/PUT /api/v1/departments/{id}/assignable-roles` | 维护可指派角色白名单，不代表部门持有权限 |
| 系统 | `GET/POST/PATCH /api/v1/systems` | 权限中心自身与课程中心注册、状态及基本元数据 |
| 角色 | `GET/POST /api/v1/systems/{system}/roles` | 查询与创建该系统角色，支持代码唯一性 |
| 角色 | `GET/PATCH /api/v1/roles/{id}` | 详情和普通字段修改，不改变 status |
| 角色 | `PUT /api/v1/roles/{id}/status` | **单独状态 API**，一并处理有效权限失效 |
| 角色 | `DELETE /api/v1/roles/{id}` | 受控退役/删除，拒绝危险级联或外键残留 |
| 角色继承 | `GET /api/v1/systems/{system}/role-hierarchy` | 返回完整 DAG，前端不能强当树 |
| 角色继承 | `POST /api/v1/roles/{seniorId}/inherits/{juniorId}` | 创建继承边；合法、重复、自环、循环、越权四类检查 |
| 角色继承 | `DELETE /api/v1/roles/{seniorId}/inherits/{juniorId}` | 删除继承边并失效相关权限 |
| 角色继承 | `GET /api/v1/roles/{id}/effective-permissions` | 直接/继承/有效权限及来源解析 |
| 角色权限 | `GET/PUT /api/v1/roles/{id}/permissions` | 直接权限查询与原子替换/增删；使用清晰版本策略 |
| 指派 | `GET/POST/DELETE /api/v1/users/{id}/role-assignments` | 部门可指派资格校验，撤销记录与审计 |
| 指派 | `GET /api/v1/users/{id}/systems/{system}/permissions` | 指定系统下有效权限，不能跨系统泄漏 |
| UI 资源 | `GET/POST/PATCH/DELETE /api/v1/systems/{system}/ui-resources` | 菜单/按钮树与稳定权限码；更新必须防止环与孤儿 |
| API 资源 | `GET/POST/PATCH /api/v1/systems/{system}/api-operations` | operationId、method、路径模版、requiredAuthority 的登记 |
| 映射 | `GET/PUT /api/v1/systems/{system}/ui-api-mappings` | 前端权限↔后端 API 显式追踪及完整性校验 |
| 授权 | `POST /api/v1/authorization/check` | 仅供受信调用方的授权决策 API；与七个外部接口区分 |
| 授权 | `GET /api/v1/authorization/explain` | 管理员按请求解释角色来源，**只为调试，不泄漏敏感策略给普通用户** |
| 日志 | `GET /api/v1/admin/audit-logs` | 权限中心后台 UI 的管理查询；可复用七个对外 `/auth/audit-logs` 的服务 |
| 运维 | `GET /actuator/health/readiness` 等 | 仅必要健康检查、受适当网络权限保护 |

这里的核心不是接口数量，而是**每一种有独立业务语义/独立授权风险的状态变更拥有清楚边界**：`PATCH /roles/{id}` 不应顺手把状态、继承和全部授权一并修改；用户部门迁移不能被伪装成普通资料修改；外部鉴权 7 接口不能误放到业务系统自身 Controller。

### 16.3 API 输入模型与错误契约

- 输入：Controller 接收 `DTO`，做存在性之外的**格式**校验（不能为空、长度、数字范围、枚举、时间顺序），然后转换成应用层 Command；身份和目标系统来自服务端上下文，不信任客户端同名字段覆盖。
- 输出：返回 `VO`（或外部已有的规范响应模型），不要直接序列化 JPA Entity/领域聚合到 HTTP。
- 领域错误：`ROLE_CYCLE`、`ROLE_NOT_ASSIGNABLE_IN_DEPARTMENT`、`CROSS_SYSTEM_ROLE`、`ROLE_DISABLED`、`PERMISSION_NOT_FOUND`、`OPERATION_NOT_REGISTERED`、`AUDIT_DUPLICATE_CONFLICT` 等**建议稳定错误码**；不同内部实现必须对齐对外错误行为。
- HTTP 状态：合同明确的外部 7 接口优先使用公开状态码；内部新管理 API 可以使用 400 格式错误、401 认证错误、403 授权失败、404 不存在、409 业务冲突、422 业务规则不满足等约定，但必须写入自身 OAS，不得同一错误一会儿 200、一会儿 500。
- 分页：建议 `page` 从 1 起，限制 `pageSize` 正整数上限并在响应返回 `total`；对用户、角色、日志都要有排序稳定性和过滤条件的复合索引。
- 更新：PATCH 使用明确字段白名单与版本号，处理“字段没传”和“传 null 要清空”的区别，不能简单把所有 null 都当忽略。
- 鉴权读取：`allowed:false` 是**正常的授权结果**，不是下游 503 错误；实际受保护业务 API 应根据这个结果给 403，且不进入业务执行。

### 16.4 服务端 API 入口覆盖校验规则

生成一个可人工审阅的清单：`targetSystem, operationId, httpMethod, pathTemplate, uiModule, uiPermissionCode, apiAuthorityCode, accessPolicy, backendController, backendMethod, auditType, testId`。初次从现有 OAS 提取，后续每次 CI 校验：

1. 受保护业务路由必须能且**只能**解析到一个 operationId；不能有路径歧义（如 `/courses/me` 与 `/courses/{id}`）。
2. 每个 operationId 在目标系统内唯一且稳定，重命名时必须有迁移/兼容策略。
3. 公共路径白名单必须是显式有限集合；未匹配路由默认拒绝，不能放入「所有 GET」或「登录态即可」大宽口子。
4. 资源按钮及关联后端 API 的覆盖检查可以标记一个 API 被多个按钮调用，也可标记一个按钮触发多个 API；不能由多对多关联直接推导出更高权限。
5. 维护两个单独测试：**前端权限投影正确**与**后端 API 真正保护正确**，防止只测前端按钮隐藏。

## 17. 数据模型、ER 与增量迁移

### 17.1 本阶段应有的**逻辑** ER（不要把逻辑名强制替换现有物理表）

```text
user 1 ── N user_role N ── 1 role 1 ── N role_permission N ── 1 permission
 │                                   │
 1                                   ├─ N role_inheritance(senior_id, junior_id) ── role
 │                                   │
 N                                   └─ N department_allowed_role N ── department
 department 1 ── N department(child)             │
                                                  └─ eligibility rule only

system 1 ── N role
system 1 ── N ui_resource(menu/button tree)
system 1 ── N api_operation
ui_resource N ── N ui_api_mapping N ── api_operation

actor/user ── N audit_log (immutable-ish)
```

注意：ER 图的 `role_inheritance` 连接同一个 Role 两次，应标出**两个不同角色名和基数**；`user_role`/`role_permission`/`ui_api_mapping` 都是有业务含义的联结实体，不要用“未定义的多对多线”敷衍。面向对象领域类图**不等于**数据库物理 ER 图，不需要把数据库每张表复制成一个充血领域实体。

### 17.2 建议字段与数据库约束清单

| 逻辑实体 | 关键字段与约束 | 迁移注意 |
|---|---|---|
| User | `id, subject UNIQUE, username/no, status, department_id, version` | 原有 employee/temporary user/账号记录需有映射；部门迁移不得破坏历史日志 |
| Department | `id,parent_id,code,name,status`；同一公司下 code 唯一 | 保留现有树；不把原始部门数据导出到无权限的公开附件 |
| System | `id,code UNIQUE,display_name,status,api_base_uri` | 部署地址应由可信配置维护，不开放任意公网转发地址 |
| Role | `id,system_id,code,status,version`，`(system_id,code)` 唯一 | 角色状态与普通字段拆开；受继承引用的角色删除须有约束 |
| Permission | `id,system_id,code,kind,status`，`(system_id,code,kind)` 唯一 | 前端与后端权限类型必须区分，不用一个不透明字符串假定所有场景 |
| UserRole | `user_id,role_id,assigned_by,assigned_at`，用户/角色唯一 | 可添加 `assignment_version`，但不将 department_id 作为授权事实来源 |
| DepartmentAllowedRole | `department_id,role_id,enabled` 唯一 | 部门资格变化触发受影响用户重新校验与撤权 |
| RolePermission | `(role_id,permission_id)` 联合唯一 | 同系统 FK/服务规则，批量修改原子生效 |
| RoleInheritance | `(senior_role_id,junior_role_id)` 联合唯一、自环禁止 | DAG 不能仅靠 SQL FK 断言保证，应用/域层必须检测并发成环 |
| UiResource | `system_id,parent_id,type,code,route,sort,enabled` | `MENU` / `BUTTON` 树，无环、子节点规则明确 |
| ApiOperation | `system_id,operation_id,method,path_pattern,required_authority,enabled` | `(system_id, operation_id)` 唯一；method+path 不得冲突 |
| UiApiMapping | `(ui_resource_id,api_operation_id)` 联合唯一 | 是配置/追踪映射，不替代 API 的后端授权 |
| TokenRevocation | `jti,expires_at,revoked_at`，jti 唯一 | 缓存与 DB 持久化策略须有一致性边界 |
| AuthorizationVersion | `system_id,scope/subject_or_role,epoch,version` | 必须能在写事务后检测版本并防陈旧缓存 |
| AuditLog | `id,request_id UNIQUE,actor_id,system_code,at,type,object_type,object_id,target,before_json,after_json,result,trace_id,hash` | 201 语义和 HTTP 请求重试不重复写；只读查询索引按 actor/at/target |

上表的 `AuthorizationVersion`、`TokenRevocation` 是**逻辑持久化要求**，具体可以用现有 MySQL 表、Redis key 和 Spring 机制达成，无须一对一新增物理表。对 JWT 令牌撤销的“Redis 失联时是否仍可验证撤销”必须给出可重建的持久策略；未验证就 default deny，而不是准许访问。

### 17.3 历史数据迁移：必须执行的顺序

1. **导出基线**：`git rev-parse HEAD`、Flyway schema_history、数据库表/索引/外键、主要实体数量、角色指派数量、现有菜单/API mapping 覆盖数，脱敏存储采样结果；发布前完整备份。
2. **定义新域映射**：多公司数据统一到单公司的逻辑组织视图；先确定需要保留哪些历史字段和兼容查询，再决定退役 company 表，而不是一句“公司表不需要”就 `DROP TABLE`。
3. **迁移账号**：如果旧用户名或 employee_no 不是新稳定 subject，建立映射表/迁移策略；重复用户名、空部门、跨公司指派等异常输出待核对清单，严禁随意合并不同自然人。
4. **迁移角色**：为旧角色确定目标 System，清理跨系统误授；建立 role hierarchy 空图或受审查的初始边，角色 ID 和权限 ID 尽量稳定；已有审计日志历史 ID 不因迁移变化。
5. **迁移 UI/API**：从现有菜单资源与新版外部课程 OpenAPI 提取，显式注册 operationId 与 requiredAuthority，**不能把所有外部 API 都默认赋给 admin**来凑联调。
6. **唯一索引前清洗**：检查重复 `(user,role)`、`(role,permission)`、`(system,operationId)`、环关系与部门角色准入；产出违规报告，修复后再加约束。
7. **重构 Flyway**：在空库和从真实旧结构升迁两条路径分别验证。
9. **双实现种子一致**：structured 和 DDD 测试各自使用独立干净库，运行同一 Flyway 与同一安全种子，不让互相影响；生产由一个活动实现执行业务写入。

### 17.4 关于“二十几张表一个子域”的正确理解

DDD 的**子域/限界上下文**按业务语言与一致性边界划分，而不是数据库表数量。一份权限中心包含用户、角色、权限、组织、授权评估、审计等多个业务功能，但不应为每张表定义一个 Bounded Context，更不应把本阶段做成七个微服务。初版可以作为一个围绕**身份与授权管理**的业务上下文；与课程中心业务模型之间通过 API/Adapter 边界交互。适配外部差异需要时可使用 ACL，但仅因为“引用外部项目”就一定强制建 ACL 没有必要。

## 18. 鉴权算法、角色继承计算、版本与一致性细则

### 18.1 统一鉴权步骤（建议在 structured/DDD 两版用相同契约测试）

```text
Authorize(subject, requestedSystem, operationId):
  1. TokenVerifier.check(signature, issuer, aud, exp, iat, jti)
     若无效 → DENY(UNAUTHENTICATED)
  2. 查目标 System 与 User；停用或不存在 → DENY
  3. 从可信路由注册表解析 ApiOperation；未登记 → DENY(OPERATION_UNREGISTERED)
  4. 获取该用户对该系统的有效直接角色
  5. 沿 senior→junior 的继承 DAG 遍历角色（包含直接角色）
     去重；停用角色及其后续路径被切断；判跨系统非法
  6. 获取每个有效角色的直接权限，合并并按 system/type 过滤
  7. 根据 ApiOperation.requiredAuthority 判断是否包含所需权限
  8. 输出 AuthorizationDecision(allowed,reason,requestId,traceId)
  9. 技术日志 / 安全审计记录结果（包括拒绝的必要元数据）
```

真实网关流程的第 3 步应发生在客户端能自由指定 operationId **之前**：网关先由可信路由 `(method,path,upstream)` 解析操作 ID，然后向权限中心调用已登记的决定接口。用户无权时按业务 API 语义映射为 403，而公开 `/auth/api-permissions/{operationId}` 本身仍返回 `{allowed:false}`。

### 18.2 循环检测与并发避免

**单请求正确性**：添加 A→B，先校验 A/B 是不同的已存在同系统角色、调用方拥有继承管理权，随后查询“B 是否已经可以到达 A”。能到达则拒绝，否则插入边。

**并发正确性**：两个客户端同时提交 A→B 和 B→A，仅用两次无锁 DFS 都可能看到“尚未有边”，然后双双提交形成环。需采用以下经证明的一种机制：

- 在每个目标系统范围对角色继承图的修改串行化：获取该 System 的**数据库行排他锁**，读取关系并检查/插入/提交；或
- 使用足够的 SERIALIZABLE 事务与有界冲突重试，并以真实 MySQL 并发测试证明无环；或
- 用明确版本化的图快照 + 条件更新，在冲突后重新读取完整图和重试（不是只给单个 Role 增加 version 而遗漏另一条边）。

异常路径必须是完整事务回滚，不能先更新缓存然后 DB 因冲突回滚导致缓存“凭空有边”。图规模若只有有限角色，优先采用系统级受控串行化使测试可解释，再优化。

### 18.3 缓存结构建议（高读少写，优先正确性）

```text
key = authz:{systemCode}:{subject}:{authorityVersion}
value = {
  directRoles: [...],
  effectiveRoles: [...],
  effectiveUiPermissions: [...],
  effectiveApiAuthorities: [...],
  buildVersion: ...
}
```

- L1：单 JVM Caffeine/内存缓存，可选。L2：Redis，主要缓存版本化权限快照；DB：用户、角色、继承和权限事实来源。
- **版本必须独立可判定**：若 L1 缓存本身持有过期版本号且长 TTL，不去检查版本就无法保证下一次请求撤权；需要共享最新版本读取、可靠失效通知的确认机制，或对敏感操作绕过不确定的 L1。不能只在本地 `@CacheEvict` 就以为 Swarm 上所有副本已失效。
- 变更写入与版本提升尽量同一 DB 事务，事务提交后再通知缓存清理；如果发布通知失败，旧条目因为版本不再一致也不能被使用。
- 多节点并发下，基于旧快照构造的新缓存不能覆盖较新版本；可使用 version-key 命名而不是固定 key，不向“旧版本命名空间”继续提供新请求。
- 授权失败的负缓存须谨慎，避免旧“无权”阻止刚授予的合法权限；同样需要版本隔离。
- 系统/用户停用及 token 撤销不能只读取角色快照中的旧状态；令牌撤销和关键状态检验的正确性优先于缓存命中。
- Redis 故障下策略：数据库可用时可经受限降级直查 DB；无法证明策略最新时拒绝（fail closed）。不得在存储故障时降级成“全部放行”。

### 18.4 五组必须证明的缓存安全时序

1. **授予**：管理者给用户新角色，成功提交 → 下次鉴权允许 → UI `/auth/me` 实时反映；多个副本一致。
2. **撤销**：管理者撤销角色，成功提交 → 后续被撤销用户的业务 API 立即拒绝 → 原 token 无需等自然到期。
3. **继承变更**：添加、删除或停用继承链节点，受影响所有上级角色用户的权限同步重算；多父备用路径仍生效。
4. **系统停用**：整系统 API 拒绝，其他系统不受影响；重新启用后按真实角色计算而不是缓存误放。
5. **延迟重填**：旧版本权限查询完成较晚，不得覆盖新版本权限；通过并发测试、版本比较与日志佐证。

## 19. DDD/GRASP 职责分配与两后端真实差异

### 19.1 结构化设计不是“代码质量较低的代名词”

结构化设计通过过程分解实现功能需求，典型 `Controller → Service（用例规则和事务脚本）→ Mapper/JPA`。所有功能仍必须安全、可测试、有事务，不能为了和 OO 区分而让结构化版缺角色继承、审核或审计。两版的**对照实验**只能比较职责归属与演进成本，不能比较不同业务需求或不同质量的实现。

### 19.2 DDD 领域对象与方法建议（非对现有代码的断言）

| 概念 | 类型/所在层 | 应由它负责的行为 | 不应放在其中的职责 | GRASP 理由 |
|---|---|---|---|---|
| `Role` | 聚合根/Domain | 角色可用状态、修改直接权限的业务不变量、启停合法性 | SQL/JPA、HTTP 返回、跨系统网络调用 | Information Expert / High Cohesion |
| `RoleHierarchy` + `RoleHierarchyPolicy` | 领域服务/Domain | 继承边方向、传递、无环规则、跨系统约束 | REST 参数格式检查、事务重试入口 | Information Expert（图全局规则） |
| `RoleAssignment` + `DepartmentRoleEligibility` | 聚合 + 领域策略 | 用户是否可被指派角色、权限提升限制 | 具体数据库 JOIN、Vue 页面状态 | High Cohesion / Creator |
| `AuthorizationPolicy` | 领域服务 | 根据有效角色与目标权限计算决定、默认拒绝 | JWT 密码学、HTTP 路由网关 | Information Expert / Pure Fabrication |
| `EffectivePermissionSet` | 值对象 | 权限集合去重、来源解释、只读视图 | 查表/自己决定 actor | Value Object / Encapsulation |
| `ApiOperation` | 实体/Domain | 系统内 method/path/operationId/requiredAuthority 不变量 | 从 HTTP Request 读取可信 URL | Information Expert |
| `UiResourceTree` | 聚合/Domain | 菜单层级合法性、父子类型和防环 | 计算老师教学班权限 | Information Expert |
| `AuditLog` | 审计记录/领域值对象 | 事实不可变表达、requestId 与脱敏字段合法性 | 外部 HTTP 协议与数据库写入细节 | Information Expert / Low Coupling |
| `AuditRepository` | Domain Port | 保存/查找审计记录的抽象能力 | 依赖 JPA Entity 类/SQL 语句 | Indirection / Dependency Inversion |
| `JpaRoleRepositoryAdapter` | Infrastructure | 领域模型↔JPA Entity、CloneFactory 转换、持久化读写 | 决定是否允许给某部门指派角色 | Adapter / Low Coupling |
| `AuthGatewayAdapter` | Infrastructure/API | 外部 HTTP 及 JWT 的技术接入、标准错误翻译 | 教学班是否属于教师 | Adapter / Indirection |
| `AssignRoleApplicationService` | Application | load→校验策略→聚合改变→save→同步审计写入→返回 | 一切细粒度领域不变量写成 500 行 if | GRASP Controller / High Cohesion |

领域对象不是随意按表命名：例如 `role_hierarchy` 是多角色关系图，创建/删除边涉及**图整体**，不适合只让其中一个 `Role` 无锁独自决定“全局无环”；这也是为什么要有 RoleHierarchyPolicy/Domain Service。领域事件也不是强制：若某个简单状态只需同步保存和审计，同步应用事务可以更清楚。

### 19.3 推荐包结构（以实际 Maven 工程修订）

```text
com.xmu.rbac.ddd
├── interfaces
│   ├── rest                    # Controller, DTO, VO, ExceptionHandler
│   ├── gateway                 # inbound authorization Gateway route adapter
│   └── assembly                # DTO -> Command, Result -> VO
├── application
│   ├── command                 # AssignRole, LinkRole, ChangeStatus ...
│   ├── service                 # use-case orchestration @Transactional
│   ├── query                   # listing/reporting, query read models
│   └── port                    # auth/audit/cache/query ports where appropriate
├── domain
│   ├── identity                # User, Status, SubjectId
│   ├── organization            # Department, DepartmentRoleEligibility
│   ├── role                    # Role, RoleAssignment, RoleHierarchyPolicy
│   ├── permission              # Permission, ApiOperation, UiResourceTree
│   ├── authorization           # AuthorizationPolicy, AuthorizationDecision
│   ├── audit                   # AuditLog and domain invariants
│   └── repository              # interfaces: RoleRepository, UserRepository etc
└── infrastructure
    ├── persistence             # JPA Entity/Repository/Adapter/Assembler
    ├── cache                   # Redis, L1 (optional), version invalidation
    ├── identity                # JWT and external SSO support
    ├── gateway                 # HTTP forwarding, operation registry
    ├── audit                   # synchronous audit log persistence
    ├── logging                 # LayerLoggingAspect + logback config
    └── config                  # Spring Bean wiring
```

**依赖倒置规则**：`domain` 不 import `jakarta.persistence.*`、`org.springframework.web.*`、Redis/HTTP client 类；`application` 可以使用 `@Transactional` 等编排技术，但不直接 import `JpaRepository`、数据库 Entity 或具体审计持久化实现；`infrastructure` 实现 Domain Port。通过 ArchUnit 校验，并用 `jdeps`/静态检查辅助。不为背术语把所有 Service 改成 AbstractFactory。

### 19.4 六个必须“外部相同、内部不同”的用例对照

| 用例 | 结构化核心顺序 | DDD 核心顺序 | 需要展示的具体设计差异 |
|---|---|---|---|
| `addRoleInheritance` | Service 直接查询边→DFS 环检测→Mapper 插入 | ApplicationService 锁图并加载→RoleHierarchyPolicy.validateLink→Repository 保存 | 环的业务规则归 Domain Service；事务和数据加载归 AppService |
| `assignRoleToUser` | Service 查询 user/dept/role/allowed list→检查→插 UserRole | AppService 加载 RoleAssignment 聚合/Eligibility→`assignment.grant(role,policy)`→Repo | DepartmentAllowedRole 不是角色权限，Domain 对象保护规则 |
| `changeRoleStatus` | Service 读 Role→if 状态合法→更新→版本+审计 | `role.disable(actor)`/`role.enable(actor)`→保存→RoleStatusChangedEvent | 角色封装状态迁移、事件表达已发生事实 |
| `getEffectivePermissions` | Service 直接循环/SQL 查询关系/权限→合并 | `AuthorizationPolicy` 与 RoleHierarchyResolver/值对象 `PermissionSet` 协作 | 计算规则明确封装，Controller 仍相同 |
| `authorizeApiOperation` | TokenInterceptor/Service 得到身份→operationId→角色权限 | API Adaptor→AuthorizationApplicationService→AuthorizationPolicy→Decision | 协作对象、边界与对外错误一致，避免空转“多一层” |
| `writeAudit` | AuditService 直接存 `audit_log` | AuditApplicationService→AuditLog/Repository→同步保存 | 审计记录作为不可变业务事实，数据持久化细节不进入 Domain |

> 开工前每个用例写下“希望区别在哪”仅用于设计取舍，实际 UML 需在代码存在后核对。`get*` 查询一般两版外部与结构都可以相似；**真正的差异重点应在涉及状态变化和复杂业务规则的命令用例**。绝不能刻意把同一业务算法结果做成不同以凑设计差异。

### 19.5 DDD、GRASP 和 Design Patterns 的展示映射

| 理论概念 | 本项目可展示的合法应用 | 何时不该强行使用 |
|---|---|---|
| Ubiquitous Language | `Role`, `System`, `DepartmentAllowedRole`, `ApiOperation`, `AuthorizationDecision` 文档/类/API 同名 | 给一个概念五种任意中文/英文名称 |
| Bounded Context | 权限中心的统一授权模型 vs 教学业务系统的业务模型 | 为每个 JPA 表都创建一个限界上下文 |
| Entity / Aggregate | Role、UserRoleAssignment、UiResourceTree 的身份、状态与一致性 | 只有 getter/setter，无任何不变量，却称其为充血聚合 |
| Value Object | `PermissionCode`, `SystemCode`, `RoleGraphEdge`, `AuthorizationDecision` 不可变表达 | 把所有数据库表都包装成值对象 |
| Repository | 面向聚合的 `RoleRepository`, `RoleHierarchyRepository` 接口 | Domain 层直接注入 JpaRepository 和 SQL Mapper |
| Information Expert | Role 判断自身启停；RoleHierarchyPolicy 判断环 | 在 Controller 包揽所有业务判定 |
| Creator | 聚合从合法输入创建角色指派或授权决定 | 无因新建一个无意义 `*Factory` |
| Controller（GRASP） | Application Service 作为用例协调者；REST Controller 为协议入口 | 把 MVC Controller 和 GRASP Controller 视为永远相同职责 |
| Low Coupling/Indirection | 外部身份/课程 API 与 JPA 通过端口和适配器隔离 | 每种小函数都强制经过三层代理 |
| High Cohesion | Role 管角色规则、Audit 管审计、AppService 管事务编排 | 一个 `CommonService` 处理全部业务 |
| Polymorphism | 确有多种实际授权资源类别或策略实现时使用统一接口 | 只有一种存储时为图面多态造两个空实现 |
| Pure Fabrication | 复杂查询/审计装配逻辑专设 Adapter/Assembler | 把所有领域行为搬到工具类造成贫血模型 |
| Adapter | `CourseIdentityContractAdapter` / `JpaRoleRepositoryAdapter` 转换外部协议或存储模型 | 无接口不匹配时引入没有实际用途的 ACL |
| Factory Method | 存在真实的可替代创建路径并由抽象创建者决定产品类型 | 用 Spring `ApplicationContext.getBean` 就直接称为严格 GoF Factory Method，或把 `CloneFactory` 字段复制称为同一模式 |

### 19.6 评价两种设计差异时必须使用的度量

- 接口/合同相同：相同的业务方法、HTTP 输入输出、状态码、权限决策、审计语义，且可跑共享黑盒测试。
- 包依赖不同：structured Service 与 JPA/Mapper 的依赖 vs DDD domain/port/adapter 的稳定依赖。
- 修改范围不同：在“新增一种角色管理规则”时两种实现需要改哪些文件；使用真实 Git diff 说明，而不是泛泛称“DDD 必然更优”。
- 可测试性不同：Domain Policy 可以纯内存单元测试；structured Service 通常通过应用/数据库集成测策略；两种都需真实 MySQL 的行为测试。
- 复杂度代价不同：DDD 需更多模型/端口/装配/对象转换；简单 CRUD 适度过程式往往更合理。这是答辩合理的取舍，而非分数高低的机械结论。

## 20. 审计系统详细设计：同步落库与故障处理

### 20.1 把审计分为三条明确的路径

**路径一：权限中心自己的敏感授权配置变更**：例如添加继承关系、赋予高权限角色、禁用用户。原则上授权变更与审计事实尽可能进入**同一个本地 MySQL 事务**，避免授权已经成功而审计未记录；不能因审计写入失败而将本地敏感授权操作报告为成功。

**路径二：课程中心业务成功后的统一身份审计**：课程 Service 完成自身 MySQL 事务，然后通过外部 `POST /auth/audit-logs` 写入权限中心的权威审计库。老师公开契约就是这样设计的。本组提供的是**审计接收、身份确认、幂等存储、授权查询服务**。

**路径三：被拒绝、被攻击或失败的安全事件**：认证/授权拒绝不应该被误记录为“业务已成功修改”；但为了追溯，必须有独立的拒绝事件（例如 `AUTHZ_DENIED`，仅带脱敏 operationId/主体/结果）。Logback 日志可立即记录；必要的拒绝审计直接同步写入 audit_log，不能造成认证接口递归。

### 20.2 同步接口与本地审计存储（必须能单独跑通）

```text
课程中心事务成功
      │
      ▼
HTTP POST /auth/audit-logs
      │
      ▼
JWT + audience + 写审计权限校验
      │
      ▼
AuditApplicationService
      │
      ├─ requestId 是否已存在？
      │     ├─ 同键同内容 → 返回既有日志（201，同一 id）
      │     └─ 同键不同内容 → 外部契约兼容的 400 + 冲突业务码
      │
      └─ 新记录：Server-derived Actor + 安全字段白名单
                        │
                        ▼
                 AuditRepository.save
                        │
                        ▼
             DB COMMIT → 201(记录对象)
```

要点：

- **严格幂等不是先查再插那么简单**。在并发请求中，对 `requestId` 的 DB 唯一索引是最终防线。先查读到不存在、两个请求同时插时，只有一个成功；另一个捕获唯一索引异常，重新读取已存在记录、比较规范化的业务 payload/hash，再决定返回原记录还是冲突。
- `requestId` 与 `payloadHash`、`sourceSystem`、`subject` 的规范化比较应在首次写入时保存。若同一个 requestId 被跨系统复用，默认视为冲突，不应该得到另一个系统记录。
- 请求中的 `objectType/objectId/target` 来自调用方业务事实，但 `actor`、服务接收时间、认证来源和授权身份由中心决定。需要区分原始事件 `occurredAt` 与权威 `recordedAt` 时，可内部多存字段，不能擅自改变外部 `at` 的约定。
- 外部 POST 若超时但 DB 已提交，调用方必须使用**原 requestId 重试**；绝不能每次重试生成新 UUID。
- 不返回完整审计对象中的加密/内部字段，也不能在异常日志中打印 before/after 全量 JSON。
- 如果课程业务写入后审计 POST 失败，而课程系统不支持任何可靠重试，则系统只实现了“尽力而为”，不满足强审计保障；必须在集成验收记录该风险。本阶段不增加消息或异步补偿机制；调用方应保留原 requestId 并在可控重试时重新同步提交。

### 20.3 审计库访问、保留与脱敏

- 中心 `GET` 查询必须强制已认证+具有审计查询权限，同时校验**系统作用域**。仅有普通课程 `student` 角色不能通过用户自行传 `actorId` 就查别人的全部日志。
- 对 `before/after` 使用字段白名单：允许角色码、资源码、状态、分数等经过确认的字段；不允许包含 `password`, `accessToken`, `refreshToken`, `Authorization`, 语音录音、原始隐私资料等。大字段/二进制内容只保留资源 ID 或安全摘要。
- 存储日志不可随便按业务删除；删除用户后 Actor 快照仍可保留非敏感、用于历史解释的最少字段，并受审计保留/隐私要求约束。
- 查询使用 `(system_code, at DESC, id DESC)`、`(actor_id, at)` 等实际 SQL profile 支持的索引；不能在 10k 员工场景先查出全表再 Java stream 过滤分页。
- 审计拒绝事件可见性应高于正常访问日志；发生数据库写入故障时优先保障安全事件和权限配置写操作的审计一致性。

### 20.4 必测故障表（针对用户新增需求单独验收）

| 编号 | 故障注入 | 必须看到的结果 |
|---|---|---|
| AUD-T01 | 同一 POST 重试 2 次，Body 完全一致 | HTTP 201，返回相同 id；DB 一条 |
| AUD-T02 | 并发 20 个请求具有相同 requestId | 最终 DB 一条，不抛出无处理的 SQL 500 |
| AUD-T03 | requestId 相同但内容不同 | 明确的冲突业务结果，历史数据不覆盖 |
| AUD-T04 | 本系统权限修改事务中途异常 | 不产生成功事实日志，业务变更与同步审计一同回滚 |
| AUD-T05 | 外部 POST 网络超时，服务端实际已入库 | 重试同 requestId 得到原 id |
| AUD-T06 | 审计事务提交前进程崩溃 | 不产生半条审计记录，数据库事务回滚 |
| AUD-T07 | 审计事务提交后服务进程崩溃 | 重启后已提交记录仍可查询，相同 requestId 重试返回原 id |
| AUD-T08 | 审计数据库不可用或写入异常 | 同步请求明确失败，不返回虚假的 201；本地敏感变更按事务回滚 |
| AUD-T09 | POST 审计请求包含非法字段或格式 | 按契约返回 400，未产生错误审计记录 |
| AUD-T10 | 普通学生试图查他人审计或写假 actor | 403/合同内错误，actor 不可篡改 |
| AUD-T11 | GET 时间范围/分页边界 | 页码、total、时间顺序正确，错误 400 |
| AUD-T12 | 角色撤销导致缓存权限变化，同时审计高并发写入 | 授权本身即时拒绝，审计同步提交且可查询 |

## 21. CloneFactory 的真实使用边界、技术检查和安全清单

### 21.1 源码性质

老师的 Gitee 代码中 `clonefactory/src/main/java/cn/edu/xmu/clonefactory/CopyProcessor.java` 是注解处理器，声明处理 `CopyFrom`、`CopyNotNullFrom`、`CopyTo`、`CopyNotNullTo`，在编译阶段生成辅助 `CloneFactory.copy(...)` / `copyNotNull(...)` 方法。`projectmgt-code-conventions` 指定同名、同类型字段优先使用该工具，但不代表所有复杂对象可以无脑深拷贝。

**需要验证**：CloneFactory 自身对应的编译级别、Annotation Processor path、生成源码包、版本/依赖与我组 Java 21 / Spring Boot 3.3.5 / Maven 插件是否兼容。老师工程可能已升级到 Spring Boot 4.x，但不应为了满足 CloneFactory 就把我组所有依赖不经验证整体升级。

### 21.2 转换场景矩阵

| 转换 | 推荐技术 | CloneFactory 的适用范围 | 明确禁止/要求显式实现 |
|---|---|---|---|
| HTTP 入参 DTO → Application Command | `CloneFactory.copy` + 字段白名单补充 | 同名同型的 name/description/status request 字段（status 更新是否允许仍由业务决定） | JWT subject、actor、角色权限、departmentId 可信来源不能从客户端拷贝覆盖 |
| Application Result → HTTP VO | `CloneFactory.copy` | id、name、code、status、时间字段同型时 | 密码哈希、私有审计追踪、内部缓存版本不应意外暴露 |
| JPA Entity → Domain Aggregate | 对象装配器显式重建 + CloneFactory 同名字段 | Role 基本属性、PermissionCode 等简单字段 | 必须调用合法的领域恢复/构造方法；不能绕开不变量、自动复制所有 ORM 关联 |
| Domain Aggregate → JPA Entity | 同名字段 CloneFactory + 显式关联设置 | 状态、名称等同型字段 | 抽象权限计算结果、继承图缓存、临时领域事件不可直接 persist |
| PATCH DTO → 持久化目标 | `copyNotNull` 仅在明确“null 表示不修改”时 | 简单可选字段 | “传 null 要清空”需要显式字段存在性标记；禁止 PATCH 覆盖 ID、actor、createdAt |
| AuditLog → AuditLogEntity | 白名单装配 + 可用的 CloneFactory | requestId、type、target、traceId 等 | before/after 脱敏、actor 服务端补齐、payloadHash 计算必须手工控制 |
| Role 集合 → EffectivePermissionSet | **领域算法** | 无 | 不能使用字段复制代替权限并集、继承 DFS、无环规则 |
| JwtClaims → AuthenticatedSubject | 显式安全校验后的映射 | 原则上不作为盲目自动复制对象 | 不可直接信任入参 claims、将 JWT 的伪造 `roles` 当授权结果 |
| External Apifox DTO → 内部 Command | 适配器 + 明确 Schema 校验 | 确实相同的字段可复制 | 多版本字段差异、时间类型、数组/嵌套对象需显式转换 |

### 21.3 代码示意（是“设计伪码”，非保证当前 CloneFactory 版本的直接可编译实例）

```java
// 示例：必须对照真实注解处理器的生成规则再写成可编译源代码。
@CopyFrom({ChangeRoleNameDTO.class})
public class ChangeRoleNameCommand {
    private Long roleId;
    private String name;
    // roleId 由 URL/用例上下文设置，不能允许 JSON 直接覆盖。
}

// Controller 层（伪码）
ChangeRoleNameCommand command = CloneFactory.copy(new ChangeRoleNameCommand(), dto);
command.setRoleId(pathRoleId);
applicationService.renameRole(command, currentSubject);
```

**安全问题**：如果 DTO 包含 `roleId` 或 `status` 与目标对象同名，生成器默认可能复制。必须使用对应 `@CopyFrom.Exclude`/`@CopyFrom.Of`（按实际版本支持情况）或专门的 Command 类，防止赋值越权；JSON 输入类尽量不包括受保护字段。

### 21.4 CloneFactory 专项测试

1. `mvn clean test` 验证生成代码存在、类名和复制重载无歧义；若修改注解不 clean，旧生成源码残留可能掩盖问题。
2. 同名字段可被复制、不同名字段不会被错误映射、不同类型字段必须显式处理。
3. `copyNotNull` 的 PATCH null 行为与接口定义一致；“清空字段”和“未提供字段”不混淆。
4. 敏感字段（password/token/privateAuditState）绝不复制到 VO。
5. Domain Aggregate 经过 Entity round-trip 后，领域方法和业务不变量仍可用；不是只剩 getter/setter。
6. 两个后端各自包含真实 CloneFactory 用例、测试和对应图；只在 DDD 使用一次没有说明结构化版本的要求时，要在设计取舍中记录原因。

### 22.2 类图与顺序图严格排版要求（从 ZIP 具体规则展开）

**类图**：

- 目标 Service 放在几何/视觉中心，模型/Repository/Adapter 分布四周，不机械将所有类向右堆叠。
- 类框有“类名 / 属性 / 操作”三段；实体、接口标注 `«interface»`；外部模型/PO/Domain 可按名称区分。
- 对象类型字段对应 Association，连线标注 Role Name；方法参数/局部变量依赖用 Dependency；实现关系从实现类指向接口，虚线 + 空心三角；依赖线不写误导性文字。
- 不允许类框重叠、连线穿过第三方类框、文本/方法溢出、无意义的折线、U 形连接；必要时画布变大。
- 类的每条重要方法必须在真实实现中存在；方法参数和返回类型不得为“图好看”随便省略到丧失可追踪性。

**顺序图**：

- 最左端调用方写为 `obj: 调用者`，之后是 Controller/Service/Repository/Domain；普通 Lifeline 采用 `objectName: ClassName`。
- 静态方法使用 `«MetaClass»` 的 Lifeline，不能把静态工厂当成某个普通实例方法来画。
- 调用方整个同步执行周期有 Execution Specification；每个被调用对象的**独立调用**有独立短执行条；同步箭头落在接收方执行条顶边的入口处。
- 未捕获异常从实际抛出方发给 caller，不画整条异常逐层传播链冒充必要消息；异常来源执行条必须仍处于激活状态。
- `alt` 表示条件互斥、`opt` 表示可选、`loop` 表示循环；循环框完整包含循环体消息和它们产生的执行条，不跨框线截断。
- 每次重新生成 SVG 后必须渲染为 PNG 并**实际目视核查**；只依赖脚本 exit 0 不足以证明 UML 清楚。

### 23.1 权限中心前端的建议页面清单

| 页面 | 应提供的交互 | 关联需求/服务端验证 |
|---|---|---|
| 登录 | 账号、密码或实际身份源认证入口；目标系统选择仅在协议许可时提供 | POST `/auth/login`；错误态和 token 管理 |

| 403 / 未授权页 | 已登录但无权给出明确原因和返回路径 | 页面导航是用户体验，真实 API 被 403 |

### 23.2 前端权限策略的详细规则

1. 首次加载页面经 `/auth/me` 取得**当前系统**角色和 UI 权限集合；按后端提供的资源树生成菜单和按钮状态。
2. 没有菜单权限时不展示或展示不可操作状态（以 UX 设计统一），但后端仍做独立强校验。
3. 角色继承改变后，当前用户权限发生变化的页面必须能重新获取授权；不允许永久保留本地旧 Pinia store 权限。
4. 对激活的路由使用统一 `routeMeta.requiredPermission` 或受控权限组件；后台无权的深链跳转由服务端 403 接住。
5. 系统切换后清空当前系统的菜单/按钮/权限缓存，只读取新系统数据；不能因同名 `admin` 把两个系统的角色混合。
6. 用户/角色/菜单/审计列表分页由后端执行，非静态模拟数组；有 loading、empty、error 与 403 四种状态。
7. 审计页日期筛选应以明确时区转换为 ISO 8601，避免跨时区遗漏。不能默默展示超出管理员权限的日志。
8. 前端后端选择是环境配置/代理 upstream，不是让用户在生产 UI 中随意输入任意后端 URL；默认 structured，切至 DDD 可通过部署配置或测试开关实现。
9. 所有与权限/审计相关的按钮至少一个能在实际后端形成三层日志；“点击仅触发前端弹窗、不发出任何请求”的虚假演示不能验收。

### 23.3 可演示的四条完整用户旅程

**旅程 J-01：角色继承与授权变化**：超级管理员登录 → 建立角色 A/B/C → 配置 B 的直接按钮权限 → 添加 A 继承 B、B 继承 C → 给普通用户仅分配 A → 用普通用户登录 → 看见经继承获得的菜单/按钮 → 删除继承边 → 页面刷新权限消失 → 直接调用旧 API 返回 403 → 查审计。

**旅程 J-02：部门准入与用户调动**：总部管理员将角色配置成仅部门 X 可指派 → X 部门管理员分配成功 → 尝试给部门 Y 人员指派失败 → 总部将用户从 X 迁至 Y → 事务按准入策略回收不合法 UserRole → 老 token 再访问也没有该权限 → 审计清楚显示调部门与撤权。

**旅程 J-03：跨系统课程 API**：用统一 subject 登录课程中心 → `/auth/me` 返回 teacher / 菜单按钮权限 → 访问课程业务 API → 网关用可信 operationId 查 API 权限 → 有权则进课程 Service → 用户不是该课程组长时由业务 Service 再拒绝 → 操作不会越权更改课程数据 → 相关 Logback 与拒绝审计可追溯。

**旅程 J-04：同步审计**：课程中心完成一次真实业务状态变更 → 带稳定 requestId POST `/auth/audit-logs` → 中心 201 返回 id → 原 requestId 重放同样 payload 返回同一 id → 有权限管理员按 actor/target/时间查询。

| API-C05 | GET 有权 API operationId | 200 `{operationId,allowed:true}` |
| API-C06 | GET 存在但无权的 API operationId | 200 `{operationId,allowed:false}` |
| API-C07 | GET 不存在的 operationId | 404，网关不放行 |
| API-C08 | POST logout | 204，无 body；旧 token 随后被拒绝 |
| API-C09 | POST audit 同 requestId 同内容 2 次 | 201 + 相同 id，一条记录 |
| API-C10 | POST audit 同 requestId 不同内容 | 合同兼容错误、无覆盖 |
| API-C11 | GET audit 按 actor/target/from/to/page/pageSize | 正确过滤、分页、Actor DTO 结构 |
| API-C12 | 无权查询 audit | 403 且不泄漏 items 数量/内容 |
| API-C13 | JWT 没 aud/iss/exp 错误 | 401，业务服务不执行 |
| API-C14 | 权限服务外部超时/503 | 网关 fail closed；503 不当作 `allowed:true` |
| API-C15 | 课程中心 Service 对象约束不成立 | 即使全局 API 允许，仍是对象级 403 |

### 24.5 等价类、边界值、异常必须落实到设计和代码

**等价类**：正确/错误密码；存在/不存在用户；正常/冻结角色；有效/停用系统；同系统/跨系统；可指派/不可指派部门；本人/他人；API 登记/未登记；审核人有权/无权；请求 ID 新建/重放/异体。

**边界值**：用户名长度空/1/最大/最大+1；分页 `page=0/1/最后一页/越界`、`pageSize=0/1/上限/上限+1`；角色 0/1/N；DAG 深度 0/1/多层；菱形；时间 `from=to`、`from>to`、跨午夜和时区；JWT 在 `exp` 边界时的判定；审计 Body 空/极大 JSON（根据已公布契约限额）。

**异常**：DB 唯一索引、并发环、事务回滚、缓存宕机/重连、网关没权限/超时、服务端 503、外部重复操作。每种异常必须有稳定业务码或明确重试策略；不以吞异常返回 200 掩盖失败。

在本项目 `pom.xml` 已可见 JaCoCo 检查规则。执行助手应先审视其激活方式，再分别运行两个模块：

```bash
# 命令模板，执行前根据实际 Maven 模块和 profile 调整
./mvnw -pl rbac-structured -am clean verify
./mvnw -pl rbac-ddd -am clean verify
```

证明包含：模块名、commit、JDK/Maven 版本、测试总数/通过/失败/跳过、行/分支覆盖、关键 RoleHierarchy/Authorization/Audit 类覆盖率与排除列表。**不能只引用 HTML 报告首页数字**而漏掉新写复杂核心类的覆盖。与老师要求比对时应同时提供测试源、API 合同和需求编号映射，不为达标扩大排除范围。

## 25. Docker Swarm 部署、网络安全、切换与现场验证

### 25.1 目标拓扑：真实两系统均在 Swarm（不只我组提供 API）

```text
公网浏览器
    │
    ▼
Swarm ingress / Nginx / 可信网关
    ├── 权限中心前端 rbac-web
    ├── 课程中心前端 course-web
    ├── 权限中心后端上游（二选一 active）
    │     ├── rbac-structured:8081（示意端口）
    │     └── rbac-ddd:8082（示意端口）
    └── 课程中心受保护业务 API
                ▲
                │ 必经中央 API 权限校验、目标 Service 二次权限
内部 Overlay 网络
    ├── MySQL / Redis
    ├── AuditLog 权威存储（同步写入）
    └── 健康检查/日志采集
```

端口只是示意，必须以真实部署文件和已占用端口调查为准。**网关不可绕过**：课程中心后端不应另公开一个未经鉴权的写入端口；如果直接暴露业务 API，也必须有自身完整的安全过滤器和对象级鉴权，不能将安全只寄托在 Nginx 页面路由。

### 25.2 配置与密钥管理

- 单一部署定义（例如 `deploy/stack.yml`）配 `RBAC_BACKEND_MODE=structured|ddd` 或明确的 nginx upstream 配置，切换一个 active 后端；默认 structured。
- 两后端构建成不同镜像版本，标注 commit hash；不能相同镜像仅更改环境变量却宣称两个设计实现。
- 外部课程中心 API baseURL/IdentityURL、JWT JWK/issuer/audience、Redis/MySQL 地址等来自 env、Swarm Secret/Config；**不提交密钥、原始 token、真实密码**。
- 对比测试的 structured/ddd 各用隔离数据库（或经严格隔离的 schema）与缓存命名空间；生产线上同一数据库**不应**无额外并发/升级方案就让两个版本同时写。
- 数据迁移前备份并固定镜像版本。部署策略先更新 DB 到两个版本兼容的 schema，再灰度更新服务，验证失败可回滚镜像/恢复 DB。
- 资源约束：在实际 2C/2G 级服务器上若要同时运行两个后端、Redis、MySQL、课程系统，要报告资源与 placement，可将 DB 放已有节点或增加资源；不能做一个理论上 Swarm 但根本启动不了的拓扑。

### 25.3 部署与验收命令模板（待有真实集群后执行，本文未运行）

```bash

# 5) 日志中检查 traceId + layer + method + result + durationMs
# 6) 用受控测试账号在两个系统执行 J-01~J-04；输出全部脱敏
```

现场证据至少包含实际 Swarm 节点/服务清单、四个 web/API 部署、网关访问路径、受保护业务 API 的 200/403 对照、后端三层 Logback、统一 POST/GET 审计、两个独立后端镜像/配置切换、JaCoCo 与 UML 对照。

### 25.4 两后端切换验证

1. 同一套固定种子初始化 structured 测试数据库和 DDD 测试数据库。
2. 默认 `rbac-web` 指向 structured，登录、角色继承、指派、审计全链路通过。
3. 通过部署配置切换上游到 DDD、刷新同一前端，不改业务组件源码；相同用户与规则得到相同输出。
4. 对比响应体时排除合法的随机 ID/时间/traceId，比较授权布尔值、角色/权限集合、错误码、操作后的数据库状态。
5. DDD 失败可回切 structured，但不得让两个实现共写同库后利用旧库数据掩盖业务实现差异。

## 28. 排除项、可选增强与第三阶段预留

**本阶段严格排除**：RBAC2 的 SSD/DSD/角色基数/先决角色、RBAC3 全部约束、临时授权、多人审批、风险评分、最小权限推荐、权限热力图、日志分析大屏、多租户和复杂数据范围过滤；不负责复刻课程中心学期/课程/提交/口试的业务后端逻辑。

**可选但要有明确投入/收益的增强**：审核前权限影响差异预览、有效权限来源路径、权限快照与性能基准压测、针对课程中心更多 operationId 的自动注册生成器、同步审计的数据库写入与查询优化。**两条审计 HTTP API 的实现不是可选项**。

**第三阶段预留，不在第二阶段启用**：SSD/DSD 规则引擎接口、角色基数约束、职责分离测试框架、函数式规则组合。如果需要为未来版本做接口设计，先写 ADR 不增加任何当前前端管理功能；不能让 “为 RBAC3 提前设计” 混淆第二阶段验收。
