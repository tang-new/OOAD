== 预填调用链：阅读后核对，不代替结论

structured：ManagementController → ManagementService.begin(授权锁/入口/上界) → scope/准入/角色校验 → UserRole或用户部门变更 → finish(版本/成功审计)。

DDD指派：DirectoryController.assign → DirectoryApplicationService.assign → lockGrants/actor/managed/upperBound → aggregate(profile).assign(role, eligibility) → DirectoryRepository.assign → done。

DDD调动：transfer → 锁用户并检查原/新范围和version → User.transfer保留目标准入交集 → save删除本人不合法assignment → 版本/审计；不修改共享RolePermission。

== 主审检查项

* [ ] 画清UserRole与DepartmentAllowedRole的两个多对多联结实体，资格不自动授权。
* [ ] 直接指派仅接收roleId，用户当前部门来自数据库；超级管理员也必须满足目标部门准入。
* [ ] 撤销检查当前管理权限、部门范围和assignment属于路径用户，不能凭曾授出就越界。
* [ ] 部门迁移只回收本人不合资格角色，其他用户及RolePermission不变；替换准入也需核对回收范围。
* [ ] 用户状态/资料/部门独立API；PATCH存在性和显式null、version与不可改字段逐项核对。
* [ ] 分页过滤、稳定顺序、万级用户场景和数据库offset边界；删除部门遇员工/子部门冲突。
* [ ] 用户停用/恢复与上界、最后管理员、tokenVersion分别与A/C/D确认。

== 数据与职责

sys_department、sys_user组织/档案列、sys_user_role、sys_department_allowed_role；与A共享User凭据、与C共享Role关联。汇总其余成员的15表关系而非自行包办。

GRASP：User掌握自己的状态/部门/直接角色，Eligibility掌握允许集合，OrganizationPolicy掌握范围；应用协调跨对象事实和事务。ER使用当前15表，旧公司/scope模型不进入现行解释。

== 必须准备的场景

* 正常：允许部门中的用户获得角色，调往仍允许的部门保留指派。
* 等价/边界：不准入、兄弟部门管理员、空角色集合、无用户/无部门、可空PATCH及分页0/1/最大值。
* 异常/并发：assignment属于别人、部门有子节点/用户、调动版本冲突；两次调动后的唯一部门与实际指派一致。
