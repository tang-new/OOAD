== 预填调用链：阅读后核对，不代替结论

structured加边：inherit → begin(锁/入口/root/冻结上界) → 读角色与现有边 → reachable(junior, senior) → save/changedUpper → finish。

DDD加边：RoleController.link → RoleApplicationService.link → lockGrants/角色与图 → RoleHierarchy.link → requireAffectedGrants（affectedBy/requireGraphGrant/upperBound）→ saveEdges → complete。

角色状态/删除：普通编辑与启停分离；删除同时追DirectoryApplicationService.deleteRole与Adapter；完成环节先完整性检查，再推进版本和本地SUCCESS审计。

== 主审检查项

* [ ] senior继承junior，允许多父；自环、重复、跨系统、反向可达和恢复损坏图均核对。
* [ ] 全局授权行锁必须先于图读取，事务持锁到提交；无锁DFS/单个Role乐观版本不足以证明并发无环。
* [ ] 特殊SUPER_ADMIN能力不能因空权限或停用被当普通角色；潜伏继承路径的检查与有效权限计算不同。
* [ ] 直接权限替换和新增继承是否检查完整新闭包/操作者变更前上界，受影响上级角色如何处理。
* [ ] 启用角色、系统或用户恢复能力时的校验路径，与B/D/E共同记录，不能只测新增边。
* [ ] 删除清关联，角色共享权限不会因一个用户调动清空；builtin、identityRole和系统边界解释清楚。
* [ ] 最后有效管理员由什么事实判定、哪些入口能间接破坏，不能把Policy名字当全部性质证明。
* [ ] Role.changeStatus当前只是状态赋值，不应在图/口试中虚构复杂状态机或不存在的领域事件。

== 数据与职责

sys_role、sys_role_permission、sys_role_hierarchy；与B交接sys_user_role/department_allowed_role清理，与D交接sys_grant_version和权限计算。

GRASP对照：结构化事务脚本集中规则；DDD图是Information Expert，应用服务是协调者，Repository/Adapter隔离持久化。S06由C负责业务完成环节、D负责版本一致性、F负责审计事务。

== 必须准备的场景

* 正常：创建角色、替换直接权限、合法加边/删边及状态切换。
* 等价/边界：无边/单边/多父、自环、重复、跨系统、空权限特殊管理员、删除缺失边、version冲突。
* 并发/故障：A→B和B→A只能一成功且落库方向匹配；业务或审计失败不保留边/版本/SUCCESS。
